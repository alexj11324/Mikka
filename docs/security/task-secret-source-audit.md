# Task secret source audit

This is a source audit for #1712, reviewed on 2026-11-08. It includes the implementation in this change and the existing credential paths it preserves. It is **not evidence that production IAM, deployment isolation, key rotation, provider revocation, or log retention have been inspected or exercised**. The delivery contract and operational acceptance requirements remain in [task-secret-delivery.md](task-secret-delivery.md).

## Custody and actual plaintext readers

“Server only” describes which code receives a value. It does not protect that value from an administrator, debugger, or process with sufficient access to that server. Likewise, a run-local file with mode `0600` remains readable by the task's OS user and root.

The shared store currently accepts `SECRETS_KEY_VERSION = 1`; that field is not evidence of automated multi-key rotation. Changing the deployment key requires an existing-row re-encryption/migration plan. Protected capabilities derive a separate encryption key and authenticated domain from the existing store key, so replacing that key also invalidates outstanding capabilities. No new secret store or independently deployed credential service is introduced by this change. See [store crypto](../../lib/secrets/crypto.ts) and [capability crypto](../../lib/secrets/egress-capability.ts).

## Transport, expiry and rotation

### Protected task secrets

[Claim issuance](../../lib/secrets/task-access.ts) sends an opaque capability and public origin/expiry metadata to the daemon. The [local SDK bridge](../../packages/daemon/src/task-secret-bridge.ts) holds that capability and gives the child a loopback endpoint with a dummy SDK key. The local bridge is an adapter, **not the plaintext security boundary**. Its process and a compromised task may copy the bearer and exercise its authorized operations until expiry.

The bearer is bound to owner, workspace or personal scope, repository, run, device, original device-token ID and attempt. It also carries the effective secret row ID and a revision digest. The application [data-plane route](../../lib/secrets/egress-route.ts) opens it for the route's run without database or session lookups. [HTTP execution](../../lib/secrets/egress-http.ts) limits method, path and headers; resolves all DNS answers to public addresses; pins the checked address to the TLS connection while retaining hostname verification; and refuses redirects. The configured canonical HTTPS origin includes its port: a non-default port is allowed only when it is part of that approved origin. There is no generic “all unsafe ports are blocked” claim.

The production application connection must use HTTPS; the final authenticated upstream request uses HTTPS. No global proxy is installed for GitHub or model traffic. Request/response sizes, concurrency and timeouts are bounded. Responses are buffered until known raw/encoded credential echoes have been checked. A malicious approved upstream can transform a credential arbitrarily, so this is not a proof against every possible response-based disclosure; debug, credential-export and untrusted echo endpoints must not be authorized.

Capabilities expire after at most 90 seconds and no later than the run lease. [Renewal](../../lib/secrets/task-renewal.ts) rides the existing heartbeat and checks the live run, permissions, effective row ID/revision, token authority and fresh time after asynchronous reads. A note-only edit does not alter the revision. Re-sealing, replacement, deletion, scope or delivery changes invalidate affected use through [run invalidation](../../lib/secrets/run-invalidation.ts) and prevent continuing renewal. An already copied bearer can remain usable for its residual lifetime, **up to 90 seconds**; an upstream operation already accepted cannot be recalled. This is bounded revocation, not immediate distributed revocation.

Cloud device-token rotation preserves the original claim lineage. The cap remains bound to `run.deviceTokenId`, even when [cloud-device renewal](../../lib/computer/cloud-device.ts) creates a successor token. A successor must be currently authenticated and match the same owner/device/workspace; renewal must additionally find the original claim token still unrevoked. This is a scoped-authority check, not a separately stored parent/child token chain. The original token may have expired through ordinary rotation. Revoking that original token prevents all successors from renewing this run's grants. Local devices require the original token itself. Revoking only one successor does not revoke sibling credentials; neither case retroactively cancels an already issued bearer.

## Deployment and observability limits

For E2B runs, the intended boundary is the task sandbox versus the separately trusted application: root inside the task may read native GitHub/model credentials and copy opaque task capabilities, but must not obtain the application's sealing key, database access or Infisical identity. [Host environment filtering](../../packages/daemon/src/env.ts) and [reserved task variables](../../packages/daemon/src/task-env.ts) reduce accidental inheritance; neither is a filesystem, process, container or hypervisor isolation mechanism.

The same requirement applies to local and self-hosted use. If the Agent shares the application's OS user, has root on its host, can inspect its environment, or controls a Docker socket/volume containing deployment credentials, it can cross the claimed boundary. Deploying the plaintext-holding service beside that Agent under the same privileges does not satisfy protected delivery. Local native credentials already available in the user's home directory also remain outside this feature's confidentiality guarantee.

[Request logging](../../lib/request-log.ts) records route templates, status, duration and safe attribution rather than request headers, bodies, query strings or token values. [Server masking](../../lib/secrets/mask.ts), [daemon masking](../../packages/daemon/src/secret-mask.ts) and the [shared capability matcher](../../packages/protocol/src/task-secrets.ts) provide additional output defenses, including bounded streaming holdback without retaining every renewed capability. The egress core returns closed error codes and does not log raw upstream exceptions or credentials. These code paths are evidence of design intent and implementation; they do not certify every deployment log sink, tracing agent, crash dump or upstream system.

## Evidence boundary

The focused [capability](../../lib/secrets/egress-capability.test.ts), [HTTP](../../lib/secrets/egress-http.test.ts), [human API](../../lib/secrets/delivery-http.test.ts), [route](../../lib/secrets/egress-route.test.ts) and [database regression](../../tests/task-secret-access.db.test.ts) files encode tamper, binding, expiry, permission-loss, fresh-clock, SSRF, DNS pinning, redirect, echo and authentication checks. The [benchmark](../../lib/secrets/egress-http.bench.ts) uses synthetic local TLS traffic and has no authority to establish production latency or successful Claude/Codex/GitHub operation.

This source audit did not run a local real PostgreSQL instance. Database regressions require the repository's real PostgreSQL 17 CI environment; a skipped test is not a pass. Production acceptance additionally needs the deployed isolation/key configuration, existing native subscription and GitHub flows, protected SDK calls, withdrawal behavior and observable performance to be exercised with appropriate non-disclosing evidence.
