# GitHub CI subscriptions

Mikka watches PRs published by a task run, using its existing GitHub App. A signed `workflow_run` or relevant PR webhook only schedules a read for an already bound task; it does not itself start a model. The webhook acknowledges after the scheduling update is durable. The existing 15-minute briefing cron provides bounded reconciliation and retry; the webhook also attempts a reconciliation after acknowledgement. Failed App deliveries are eligible for the existing bounded redelivery process. No repository workflow changes are required.

The reader obtains a repository-scoped installation token with read access to pull requests, checks and commit statuses; Actions read access is used to discover current-head workflow runs and recover missing workflow completion events; Contents read is used to read the PR base branch protection. It verifies the PR is open, still belongs to the task branch and repository, and reads current-head checks, statuses and Actions runs, plus required check contexts from the target branch and active rulesets. A missing required context, queued or running workflow, unavailable protection information or unknown required reusable workflow keeps the result pending or produces a visible error. Permission, network and incomplete or oversized responses fail closed and are recorded for retry; they are not successes. The watch remains active for 48 hours after publication or a relevant webhook. Later relevant events can reactivate it; a third-party check that appears after the watch expires without a GitHub Actions or PR event is not observed. Known Actions runs are also discovered by head and branch, including attempts whose webhooks were missed; runs outside that provider view are not guaranteed to be discovered.

All registered checks and known same-commit/branch Actions runs must finish; this conservative scope also includes push and manually dispatched workflows, not only PR-triggered workflows. For workflow failures, the latest completed run per workflow and event is used; all unfinished runs still hold the result pending. If an older run was rerun after another run was created and the ordering is ambiguous, Mikka waits rather than hiding a possible failure. Failure, cancellation, timeout, action-required, stale and startup failure are failures. Skipped and neutral checks are non-failing but do not alone establish success; an all-skipped/neutral snapshot or an unknown conclusion stays pending. A success needs at least one successful check or status and no failed checks. A complete snapshot must remain unchanged for at least two minutes before dispatch; normal cron cadence can make delivery later. The bounded quiet window cannot prove a provider will not register a check later: a later changed snapshot can result in another follow-up for the same SHA. GitHub's check-run API only covers the 1,000 most recent check suites; this implementation cannot detect every provider-side suite truncation. It fails closed when its own response limits are exceeded and does not claim complete coverage beyond the provider's limit.

A durable fingerprint and task-scoped dispatch key coalesce duplicate deliveries and concurrent workers; a rerun with a changed snapshot is a new result. Before the daemon receives a follow-up, Mikka rechecks the person's GitHub access, PR head and complete checks and requires the original session, device, agent and repository. An unavailable provider is retried without assuming success; stale queued results are retired. A CI follow-up does not silently fall back to a new session. CI-created commits are watched too, with at most two automatic follow-up generations before a durable Coordinator attention event requests human review. Subscription-bound original sessions are currently unsupported; a durable notice reports this rather than silently starting a different session. Selected baseline and active skills can continue only when the original session mount, immutable receipt and current eligibility remain valid. Evaluation runs, revoked skills and missing provenance fail closed with a durable notice.

Deployment requires applying the new database migrations and deploying the app; the existing 15-minute scheduled worker must remain active. The App and its repository installation must grant Actions, Checks, Commit statuses, Contents and Pull requests read access; no new event subscriptions or persistent permissions are added by this change. A 202 response establishes durable scheduling only, not completed reconciliation or Agent execution. Tests with synthetic GitHub responses do not prove a live App installation or production OAuth path.
