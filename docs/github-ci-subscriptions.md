# GitHub CI subscriptions

Mikka watches PRs published by a task run, using its existing GitHub App. A signed `workflow_run` or relevant PR webhook only schedules a read for an already bound task; it does not itself start a model. The webhook acknowledges after the scheduling update is durable. The existing 15-minute briefing cron provides bounded reconciliation and retry; the webhook also attempts a reconciliation after acknowledgement. Failed App deliveries are eligible for the existing bounded redelivery process. No repository workflow changes are required.

The reader obtains a repository-scoped installation token with read access to pull requests, checks and commit statuses; Actions read access is used to recover missing workflow completion events. It verifies the PR is open, still belongs to the task branch and repository, and reads the current head, check runs and combined status contexts. Permission, network and incomplete or oversized responses fail closed and are recorded for retry; they are not successes. The watch remains active for 48 hours after publication or a relevant webhook. Later relevant events can reactivate it; a third-party check that appears after the watch expires without a GitHub Actions or PR event is not observed. Known pending Actions attempts are refreshed through the Actions API, but a new attempt is not detectable if all its webhooks are lost and its check/status snapshot is unchanged.

All known checks must finish. Failure, cancellation, timeout, action-required, stale and startup failure are failures. Skipped and neutral checks are non-failing but do not alone establish success; an all-skipped/neutral snapshot or an unknown conclusion stays pending. A success needs at least one successful check or status and no failed checks. A complete snapshot must remain unchanged for at least two minutes before dispatch; normal cron cadence can make delivery later. The bounded quiet window cannot prove a provider will not register a check later: a later changed snapshot can result in another follow-up for the same SHA. GitHub's check-run API only covers the 1,000 most recent check suites; this implementation cannot detect every provider-side suite truncation. It fails closed when its own response limits are exceeded and does not claim complete coverage beyond the provider's limit.

A durable fingerprint and task-scoped dispatch key coalesce duplicate deliveries and concurrent workers; a rerun with a changed snapshot is a new result. Before the daemon receives a follow-up, Mikka rechecks the person's GitHub access, PR head and complete checks and requires the original session, device, agent and repository. An unavailable provider is retried without assuming success; stale queued results are retired. A CI follow-up does not silently fall back to a new session. CI-created commits are watched too, with at most two automatic follow-up generations before a durable Coordinator attention event requests human review. Subscription-bound workers and runs with selected skills are currently unsupported for original-session CI follow-ups; they remain pending rather than falling back to a different session.

Deployment requires applying the new database migrations and deploying the app; the existing 15-minute scheduled worker must remain active. The App and its repository installation must grant Actions, Checks, Commit statuses and Pull requests read access; no new event subscriptions or persistent permissions are added by this change. A 202 response establishes durable scheduling only, not completed reconciliation or Agent execution. Tests with synthetic GitHub responses do not prove a live App installation or production OAuth path.
