# Runtime observability (PostHog)

The API and daemon send OpenTelemetry traces and structured logs to PostHog.
A runtime keeps one W3C trace across requests, Workflow steps, dispatch, cloud
startup, agent work and completion; model generations and masked browser
replays attach to the same operational context.
Group by route and caller to find who drives database transfer, instead of
diffing `pg_stat_statements`. This adds to the
[database transfer monitoring](database-egress.md); the ops snapshot and the
`db_sample` / `db_transport_sample` logs are unchanged.

## What is traced

Mikka's independent Node API (`apps/api`) and the daemon's own operations (service
`mikka-daemon`, see [Daemon](#daemon)). Mikka records its own runtime stages and
numeric model receipts from the adapters, not the text or internal activity of
a user's Claude Code or Codex session. The mobile app sends trace context, not
spans (see [Mobile app](#mobile-app)).

- API server spans: `apps/api/runtime/request-trace.ts` starts
  `<METHOD> <route template>` from the generated route inventory and extracts
  the standard `traceparent`/`tracestate` carrier and bounded correlation IDs.
  Arbitrary baggage and content-bearing request headers are not propagated. H3 ends the span when the
  actual response is disposed, including streamed responses, before deferred
  jobs run. The Vite frontend does not produce Next server-render spans.
- One `pg.query:<COMMAND> <db>` span per statement, from
  `@opentelemetry/instrumentation-pg` on the `pg` pool behind `lib/db`
  (drizzle `node-postgres`). Statements outside any span are not traced, and
  neither are connect spans.
- Background work, each as a labelled job (see [Background work](#background-work)):
  `after()` callbacks, Workflow steps and cron handlers.

Every span has `service.name=mikka-web` and `deployment.environment`
(`production`, `preview` or `dev`) as resource attributes, and:

| Attribute | Meaning |
| --- | --- |
| `mikka.route` | Grouping key: the `withRequestLog('/api/…')` route, the `withDatabaseOperation('/actions/…')` action, a background job (`after:<job>`, `cron:<name>`, `workflow:<workflow>/<step>`), or the generated API route template |
| `mikka.client_kind` | `daemon` (`/v1/*`, `/api/runs/mcp/*`, `/api/runs/github-token`), `mobile` (`/api/mobile/*`, or any other `/api/*` request the iOS app sends; see [Mobile app](#mobile-app)), `cron` (`/api/cron/*`, `cron:` jobs), `workflow` (Workflow steps, `/.well-known/workflow/*`), `background` (`after:` jobs), `worker` (`/api/webhooks/*`) or `web` |
| `mikka.app.version` | The iOS app's version (`1.2.3`), on `mobile` spans only |
| `mikka.request_id` | Internal request invocation UUID, generated by `withRequestLog` before authentication. Joins early authentication queries to the same request; never copied from caller headers |
| `mikka.user_id_hash` | The authenticated account's existing salted SHA-256 prefix (16 hex characters), when known. Matches `userIdHash` in request logs; never an email, raw account ID or client-supplied PostHog identity |
| `mikka.rpc.action` | A key confirmed present in the shared browser/desktop RPC registry. No arguments or unknown action strings are exported |
| `error.type`, `mikka.error.code`, `mikka.error.detail` | On a failed request or job: the error's class name, and the code and detail of the first coded error in its cause chain (`@mikka/protocol/tracing`). Never the message |

Each call to the default model (Mikka 默认, `lib/abuse/zerocat.ts`) also writes
one `model.route` span, and the same values as a `default_model_route` log line:

| Attribute | Meaning |
| --- | --- |
| `mikka.model.id` | `deepseek/deepseek-v4.1-flash` |
| `mikka.model.route` | `zerocat` (the main route) or `gateway` (the fallback) |
| `mikka.model.fallback_reason` | On `gateway` only: `unconfigured`, `endpoint_unexpected`, `route_denied`, `paused` (ZeroCat failed in this instance in the last 60 s and was skipped), `timeout`, `rate_limited`, `quota`, `server_error`, `redirect` (ZeroCat answered with a redirect, which the transport refuses), `network`, `request_rejected` or `stream_error` |
| `mikka.model.zerocat_error`, `mikka.model.zerocat_error_code` | On a ZeroCat failure: the error names along its cause chain (`AI_APICallError>TypeError>Error`) and the first system code in it (`ECONNRESET`, `UND_ERR_CONNECT_TIMEOUT` …). Never a message |
| `mikka.model.zerocat_ms` | How long the ZeroCat attempt took, success or failure |
| `mikka.model.zerocat_status` | ZeroCat's HTTP status, when the failure had one |
| `mikka.model.gateway_credential` | On `gateway`: `system` (Vercel bills) or `byok` (our own provider key), from Gateway's routing receipt |

Count fallbacks by `attributes['mikka.model.fallback_reason']` on
`posthog.trace_spans` where `name = 'model.route'` and
`attributes['mikka.model.route'] = 'gateway'`.

Database spans also have:

| Attribute | Meaning |
| --- | --- |
| `db.operation` | Command tag (`SELECT`, `UPDATE`, `BEGIN` …) |
| `mikka.db.statement_id` | sha256 prefix of the SQL text, the same as `statement` in `db_sample` log lines |
| `db.query.text` | Parameterized SQL, literals replaced by `?`, cut to 200 characters |
| `db.response.returned_rows` | Rows returned or affected |
| `mikka.db.response_bytes_approx` | Result JSON size, estimated from the first 50 rows (not wire bytes) |

## Runtime initialization

`apps/api/scripts/finalize-build.mjs` compiles
`apps/api/runtime/tracing-start.ts`, which calls `lib/tracing/node.ts`, with pg
and OpenTelemetry packages left external. Every Vercel function, including the
Workflow handlers, starts through `mikka-entry.mjs`: it imports tracing first,
then dynamically imports Nitro's generated application. The function's queue,
duration and streaming metadata stay intact. The independent Node server and
Docker adapter use the same ordering through their generated entry wrappers.

The development launcher (`apps/api/scripts/dev.mjs`) wraps each Nitro worker
entry in the same order, including workers replaced during hot reload. This
must happen before application modules load pg; a Nitro plugin alone is too
late for database instrumentation. `.vercel/output/mikka-build.json` or
`.output/mikka-build.json` records the compiled tracing hash. An artifact hash
proves the entry was packaged, not that production spans reached PostHog.

## Mobile app

The iOS app exports no spans of its own. Every request it sends to Mikka's
`/api/*` (`apps/mobile/lib/tracing.ts`, from `@mikka/protocol/trace-context`)
carries:

- `traceparent`: a fresh W3C trace context per request, flagged not sampled.
  The server's sampler decides as for any caller, so the app cannot force a
  trace to be kept. The server's spans join that trace id.
- `x-mikka-client-kind: mobile` and `x-mikka-app-version` (only a numeric
  `x.y.z` version; anything else is left out).

`withRequestLog` stamps `mikka.client_kind=mobile` and `mikka.app.version` on
the request's span, and child spans inherit them. The headers are attribution
only, never authentication, and are ignored on machine routes
(`/api/cron/*`, `/api/webhooks/*`, `/api/runs/*`) and `/v1/*`. Requests to other
hosts (uploads, OAuth providers) get no headers.

## Daemon

`packages/daemon/src/tracing.ts` traces Mikka's own daemon operations on the
user's computer, as service `mikka-daemon`:

| Span | What |
| --- | --- |
| `daemon.run` | One run, from start to its end; `mikka.outcome` is the run's stop reason (`submitted`, `turn_ended`, `cancelled`, `error` …) |
| `daemon.run.repository`, `daemon.run.worktree`, `daemon.adapter.start` | The run's start-up stages; `daemon.adapter.start` is where a harness that cannot start fails (`subscription_local_runtime_unavailable`) |
| `daemon.run.lease` | Claiming a run from the server |
| `daemon.tool_approval`, `daemon.tool_approval.refused` | Preparing the run's tool-approval gate; a liveness refusal |
| `daemon.gateway.connect` | Opening the device gateway socket, until it opens or fails |
| `GET /v1/devices/[id]/…` | Every call to the server, named by route template (ids become `[id]`, no query), with `http.response.status_code` |

Each span has `mikka.client_kind=daemon`, `mikka.harness`, `mikka.outcome`,
and, when available, the opaque run/thread/task/Workflow IDs listed below.
Older data has `mikka.run.id_hash` (a sha256 prefix); it remains a legacy
correlation field rather than the new run lookup key. Failures carry
`error.type`, `mikka.error.code` and `mikka.error.detail`. Filter the error
code with `mikka.error.code = subscription_local_runtime_unavailable` to see
why runs fail on users' computers.

- **Joining the server's trace.** The run payload carries the dispatch trace
  context into daemon startup. `daemon.run` continues that parent; outbound
  `/v1/*` calls carry the current span's context back to the API. The run's
  completion/outbox delivery retains the same bounded carrier. A polling or
  unrelated daemon request can still have its own trace.
- **Settings.** The server hands them over in the device registration
  response (`tracing`: endpoint, the public `phc_` project token, sample rate,
  environment); `daemonTraceSettings()` in `lib/tracing/config.ts` sends them
  only for the PostHog endpoint and only when server tracing is on. A daemon
  never gets a personal key.
- **Sampling and turning it off.** The server's ordinary rate defaults to 10%.
  The daemon continues an incoming retained run parent, so critical runs stay
  complete. `MIKKA_DAEMON_TRACE_SAMPLE_RATE` can lower the ordinary rate;
  `0`, or `MIKKA_DAEMON_TRACING=0`, remains a kill switch.
  Every known sampling decision exports its effective `mikka.trace.sample_rate`
  on both spans and stage logs, plus `mikka.trace.critical` and
  `mikka.trace.retention`. Independent critical roots use rate `1`. Fast ordinary
  local trees use the actual configured rate (`head`); local errors, HTTP failures
  and operations at least 1000 ms retain their recorded local tree at rate `1`
  (`error_or_slow`). The buffer is bounded to 256 traces and 512 spans per trace;
  an over-capacity tree can be dropped. Critical paths bypass this buffer.
  Local children inherit the parent's actual weight. Run/bootstrap JSON can
  carry a validated `sampleRate` captured from the actual parent span; HTTP
  headers never carry it. A known remote parent's rate stays unchanged (`parent`):
  local retention cannot recover upstream spans. An unfamiliar remote parent
  without a rate is explicitly `parent_unknown`, with no fabricated numeric
  weight. Remote unsampled parents remain unsampled. Historical SQL fallback
  rates are estimates for those unknown/legacy rows, not measured weights.
- **Never blocks.** A batch processor exports every 10 s from a queue of 512
  (then drops). A failed or thrown export drops its spans and pauses exporting
  for a minute; shutdown waits at most 2 s. Nothing is registered globally,
  so an agent SDK's own OpenTelemetry is unaffected.
- **Privacy.** Only an allowlist of attributes leaves the computer; strings
  go through the same rules as the server (`@mikka/protocol/tracing`
  `scrubString`), and paths under a home directory become `[home]`. No
  prompts, model output, tool arguments, file content, environment variables,
  credentials or emails leave the process. Bounded opaque IDs, model labels,
  token/cache counts, timing and provider cost receipts are allowed. Startup
  phase spans from #1505/#1508 and prompt hash/version metadata from #1506/#1500
  remain available. CLI activity text is never telemetry. Tests cover this in
  `packages/daemon/src/tracing.test.ts` and the adapter metric tests.

## Background work

Work with no request of its own runs as a job, labelled by
`lib/tracing/jobs.ts` (`runJob`) and `lib/tracing/labels.ts`. The label is
also the `route` of its `db_sample` log lines, which the egress monitor
groups like a route.

| Work | Label | Kind | Span |
| --- | --- | --- | --- |
| `after()` callbacks (coordinator wakes, live notifications, issue effects, webhook ingest, device wakes …) | `after:<job>` | `background` | Child of the scheduling context, even after the response ends; a root only when no valid parent exists |
| Fan-out a cron handler defers with `after()` | `cron:<name>/<part>` | `cron` | Continues the scheduling trace |
| Cron handlers (`app/api/cron/*`: run recovery and lease sweeps, coordinator wake recovery, the ops/egress monitor …) | `cron:<name>` | `cron` | Child of the cron request's span |
| Workflow steps (every `'use step'` body) | `workflow:<workflow>/<step>` | `workflow` | Continues the durable SDK trace carrier, including opaque Mikka correlation IDs |

- Schedule deferred work with `afterJob('after:<job>', task)` from
  `lib/background.ts`, never the `next/server` compatibility adapter's `after`
  directly (oxlint `no-restricted-imports`). The adapter binds callbacks to the
  scheduling request's async context. Its `AfterQueue` starts them at H3's
  actual response-disposal boundary, with their complete lifetime retained by
  `waitUntil`. A bare `after()` would keep the request's route and parent its
  queries to a request span that has already ended. `afterJob` enters the job
  inside that callback, after the context is restored, so the job's label is
  the one in force. Do not bind the task
  with `AsyncLocalStorage.bind`/`snapshot`: entering it would restore the
  request's context over the label. Work that must keep its scheduling
  context when called back from elsewhere (live notifications) passes
  `retainContext`, which binds outside the job. The only bare `after()` calls left hand over promises
  already running in their webhook (Slack, Telegram) or flush analytics.
- Wrap a cron handler with `cronJob('<name>', handler)`.
- Workflow step labels still come from `getStepMetadata()`. The registered
  propagator also serializes the bounded Mikka carrier with the Workflow SDK's
  durable `traceCarrier`, so later deliveries rejoin the originating trace.
  SDK span names are normalized to `workflow.execute` and `step.execute`;
  bounded workflow/step names remain in `mikka.workflow` and `mikka.step`.
  The exporter normalizes these after the SDK has populated its attributes,
  and the correlated Logs use the same names.
- Job names are fixed strings, never ids or user data.
- Coordinator, dispatch, run, Factory and computer jobs are critical paths.
  Unrelated root jobs use the ordinary rate; child jobs retain their ancestry.

`requireParentSpan` stays on, so a statement outside every span is still not
traced. Turning it off would make each such statement its own single-span
trace, labelled from a stack trace: in the bundled server those frames refer
to generated Nitro chunks, not stable source module names, and capturing a
stack on every unparented query costs CPU on hot paths. Labelling the entry points instead
gives every background statement a parent, a real name and a trace.

## Querying

In the PostHog app: **Tracing** (`https://us.posthog.com/tracing`), filter
service `mikka-web`, then by attribute, for example `mikka.client_kind = daemon`
or `mikka.route = /v1/devices/[deviceId]/commands`.

For Agent queries and operations, use `posthog-cli api`. Before the first
PostHog command in a session, read its full `--agent-help` output, then list
skills and install/read the matching skill as `AGENTS.md` requires.

```sh
posthog-cli api --agent-help
posthog-cli api skill list
```

Use the installed guide's schema-discovery steps to find `query-apm-spans`.
`flatSpans: true` returns database spans directly. The following is a query
payload to validate against the discovered CLI schema.

```json
{ "query": { "serviceNames": ["mikka-web"], "flatSpans": true, "dateRange": { "date_from": "-6h" },
  "filterGroup": [{ "key": "mikka.client_kind", "operator": "exact", "type": "span_attribute", "value": "daemon" },
                  { "key": "db.operation", "operator": "is_set", "type": "span_attribute" }] } }
```

Discover `apm-attributes-list` and `apm-attribute-values-list` for attribute
keys/values, and `apm-trace-get` for one trace's tree through the same CLI. Counts now mix full
retention and sampling. Estimate totals with each span's
`1 / mikka.trace.sample_rate`, not a single global multiplier; historical
records without that field use the previous 0.1 rate.

## Dashboard and alerts

The [「Mikka 数据库与错误」 dashboard](https://us.posthog.com/project/670821/dashboard/2306506)
answers "who drives database transfer, and what fails" without SQL. Its
collection health lives on the
[monitoring dashboard](https://us.posthog.com/project/670821/dashboard/2297143).

Read every number on it this way:

- **Counts use per-span weights.** Critical spans and retained errors/slow
  requests have rate 1; ordinary retained spans normally have rate 0.1.
  `sampled_*` columns are what arrived; `estimated_*_weighted` sum
  `1 / coalesce(toFloatOrNull(attributes['mikka.trace.sample_rate']), 0.1)`.
  The 0.1 fallback preserves the historical convention, including old explicit
  acceptance traffic whose original rate was not recorded. Missing telemetry
  cannot be reconstructed by this estimator.
- **Bytes are not Neon's bytes.** `mikka.db.response_bytes_approx` is the
  JSON size of the returned rows, estimated from the first 50 rows. It ranks
  routes and statements; it is not network transfer and not the bill. The
  budget tiles and alerts use Neon's own numbers from the ops snapshot
  ([database transfer](database-egress.md)).
- **Hours are UTC**; the project's time zone is Asia/Shanghai. Hours with no
  spans are left out, not drawn as zero.
- **Error counts are spans** with `status_code = 2`, grouped by
  `mikka.error.code` (else `error.type`); one failed request can produce
  several.

### Alerts

Five alerts, the plan's limit. All check hourly and email the subscribed
users (Alex). In each alert's email, the `source` column names the route or
error code and its numbers.

| Alert | Fires when | Tune |
| --- | --- | --- |
| Mikka transfer reaches 50% of 500 GB plan allowance | The billing period's Neon transfer reaches 50% of the Launch plan's 500 GB (`monthly-budget.sql`) | The threshold `upper: 0.5` in `ALERTS` |
| Mikka monitoring collection failed or heartbeat absent | No healthy ops snapshot in the last hour (`heartbeat.sql`) | — |
| [1324] Mikka 来源数据库小时异常 | One `mikka-web` route's weighted DB queries in the last full UTC hour exceed `max(3 × its 7-day hourly median, 2000)`, or its weighted JSON bytes exceed `max(3 × median, 10 MB)`. Needs 24 covered full hours after that route first appears; bytes require ≥95% weighted coverage (`alert-source-anomaly.sql`) | `3 *` and the floors `2000` / `10000000` in `metrics`; `covered_hours >= 24` for route-specific warm-up |
| [1324] Mikka 日速率外推超过500GB月额度 | Today's Neon transfer so far, scaled to 24 h and to the month's days, exceeds 500 GB. Only from 03:00 UTC, with a snapshot ≤60 min and provider data ≤180 min old (`alert-daily-pace.sql`) | `500000000000` (the allowance) and `utc_hours >= 3` |
| [1324] Mikka 错误码小时突增 | One service's weighted error spans for one code in the last full UTC hour exceed `max(3 × its 7-day hourly median, 50)`, after 24 observed hours. Weight is `1 / sample_rate`, with legacy missing rates treated as `0.1`. Known handled Workflow hook 404, duplicate 409 and terminal 410 chains are excluded only with their own successful entry, proved by exact ancestry or an invocation-to-delivery span link (`alert-error-spike.sql`). | `3 *` and the floor `50` in `metrics` |

The Workflow filter follows individual invocations within a continuous trace.
A known hook lookup 404 must belong to that successful `after:workflow-wake`,
or to that successful `cron:reconcile` and its 2xx HTTP request. A known event
409/410 must belong to the SDK invocation tied to the exact successful 2xx
`workflow.route.flow` delivery. Continuous mode uses its single native span
link; legacy linked mode can use its exact local parent. Both allow the SDK's
one known `vqs.process` consumer span between the invocation and delivery,
with that consumer also successful. A link to a prior run origin does not
establish delivery success by itself. The filter removes only the
closed HTTP/SDK error pair and its recognized error wrapper; other errors stay
visible. With neither a valid local parent chain nor a valid delivery link,
the error remains in the alert. A successful root or another successful
invocation in the same trace cannot excuse this invocation's failure.

Every alert query returns exactly one row and the alert reads it
(`first_row`). PostHog refuses an `any_row` alert whose query its `LIMIT`
cuts short, and production has more routes than that limit. The two hourly
queries rate each source (`per_source`: 1 breach, 0 none, `NULL` without
current telemetry) and return the worst value; `source` names up to five
breaching sources, worst first, or the heaviest one when none breaches.
`NULL` (no current telemetry) does not fire; the heartbeat alert covers
collection.

The source alert fills zero-query hours only after the route's first partial
hour has ended, and only while the service has telemetry. A new desktop route
cannot inherit days of zero history from an older web service. The absolute
2,000-query / 10-MB floors still apply after warm-up, including when the
historical median is zero.

Each source's alert text includes its three largest authenticated user-hash
groups and five largest registered RPC-action groups by weighted query count,
plus the total groups and unattributed counts. Earlier authentication spans can
be attributed through their internal request UUID only when that same request
has exactly one observed authenticated hash/action. It never uses an entire
trace to infer the user, or treats a caller-supplied analytics identity as
authentication. Missing and conflicting metadata remain `unattributed`,
including data collected before these fields were deployed. The enrichment
reads only the evaluated hour; it adds no production database reads.

### Desktop startup and login query counts

The existing Desktop lifecycle acceptance saves `queryCounts` in `lifecycle.json`.
It reads the already-instrumented primary API process's cumulative counter
before and after each short window, without resetting it. The receipt binds
every snapshot to the source revision, API origin, process ID, runtime and
platform. A changed process, decreasing counter, unknown reading or unavailable
instrumentation fails the measurement.

The login comparison uses the same leased account, fixture workspace, locale
and backend. Both sides perform the ordinary email sign-in and get-session
flow. Native then completes the real browser-to-app PKCE handoff; Web uses the
freshly verified session in a new Chromium context. Each window ends when the
same seeded workspace and composer are usable. This measures ordinary business
login, not a new Google/GitHub OAuth challenge. Native handoff can overlap its
automatic renderer loading, so the receipt keeps that overlapping segment
together instead of inventing separate totals.
The short Web comparison finishes and closes before native authentication.
Better Auth's multi-session plugin replaces an earlier same-account session
in that browser cookie jar, and the PKCE handoff retains that session. Keeping
native authentication last preserves its ordinary session for the subsequent
bundled and hosted lifecycle checks without an extra login or relaxed expiry.

A validated PKCE confirmation page in the system browser reads only
`desktop.session` and the public login configuration. It does not initialize
workspace authorization, onboarding or owner-evaluated features that the
confirmation card cannot use. This applies only to the exact Web sign-in
route with a valid handoff and no OAuth or Composio continuation. The installed
renderer still requests its full bootstrap. Leaving the confirmation page
requires a fresh workspace bootstrap, even when the workspace selector stays
empty; identity-only data cannot mount workspace readers. Both the existing
owner/session fence and the current bootstrap phase reject obsolete responses.

The installed renderer groups eligible workspace reads that become ready in
the same browser turn into a bounded `desktop.readBatch`. One posted task lets
already-resolved hydration promises settle before the group is sent; its two
MessageChannel ports close before the flush. Each item retains its
registered argument schema and original authorization. Bootstrap, sign-in,
account/workspace switches, credentials, catalog loading and explicit writes
remain separate. The allowlisted views may perform their existing idempotent
initialization; this is not a database `READ ONLY` transaction. Batches share
only the current request's workspace memo and real owner/revision reads, never
a cross-request authorization cache. Revision keys are combined before each
reader proceeds to its data, preserving the original Live catch-up behavior.
The validated batch declares only its existing owner-list revision kinds. Once
an original reader resolves its real personal home, it can read those home
counters together, including a sibling whose workspace lookup finishes later.
Each reader receives only its original keys and keeps the conservative earlier
revision. Selected-team and entity keys still follow their original readers.
If a later reader fails, its planned home counter can be unused; no extra SQL
statement or response key is introduced, but this is not zero extra bytes for
every failed batch.
No task/thread list is truncated or substituted for another. Queued reads are
discarded when their owner/session/workspace generation retires, and in-flight
responses retain Main's existing identity fence. There is no timed collection
window. An older server's explicit unknown-action response is the only reason
to fall back to individual reads; transport failures do not replay a batch.
Native task-run, bot-summary and bot-roster readers return their original
snapshot, so its actual HTTP dispatch can prove Live readiness coverage. That
proof stays attached to the same response object, including its own batch item.
Merged issue, thread and chat results retain their existing catch-up checks.

Startup counts come from the first pair of the unchanged five-pair lifecycle:
bundled Electron versus the preserved hosted Web renderer in the same compiled
Electron shell, with retained authenticated state and the same warm backend.
The hosted startup sample is not presented as an independent Chrome launch.

Counts are actual `pg.Client.query` calls and PostgreSQL protocol bytes, without
sampling. All concurrent traffic in that API process remains included. Fixture
and lease/session tracking use the separate harness process and are excluded,
as are connection handshakes and TCP/TLS overhead. In-flight response bytes may
cross a checkpoint; the raw snapshots and UTC boundaries remain in the receipt.
These are query/transport measurements, not provider billing. Read the actual
paired values and investigate repeated RPC actions; screenshot counts or unit
test success do not supply the missing measurement. This adds no long idle run
and no latency pass/fail threshold.

After the existing samples and cleanup, `queryCounts.rpcActions` reads at most
16 MiB of that primary API's existing private log once. It pairs request starts
and completions in memory, then retains only the two RPC routes, registered-action
shapes, HTTP status counts and window counts. `startedInWindow` counts requests
whose start is in the half-open measurement window; completions, confirmed
crossings and missing boundaries are separate and must not be added together.
These aggregate counts are RPC invocations, not per-action SQL counts. This
projection discards internal IDs; raw logs and user hashes never enter the
artifact. Missing, oversized, truncated,
invalid or unpaired records explicitly make this diagnosis incomplete; unavailable
windows do not become zero counts.
The same log snapshot also groups calls by the existing authentication, handoff
and workspace-selection checkpoint intervals. Closed phase names and contiguous
boundaries are validated before reporting those groups; they add no request or
database read. These groups distinguish a handoff read from a required workspace
authorization read, without assigning guessed SQL counts to either. A missing
startup window keeps the overall report incomplete while independently complete
login records retain their own status.

`rpcActions.windows` continues to count physical HTTP requests. The separate
`rpcActions.logical.windows` counts ordinary RPCs once and batch items once,
excluding the batch envelope. Every item has a paired `rpc_action_started` /
`rpc_action` receipt with its own invocation ID, parent HTTP invocation ID,
fixed action, status and duration. The parent completion's `rpcItemCount`
detects even a missing whole pair. The diagnostic verifies parent identity,
route and time containment; incomplete logical evidence stays incomplete.
This aggregate projection uses internal IDs only while pairing the records.
Each item also owns an ordinary sampled span and independent metadata scope,
so parallel reads cannot overwrite another action's SQL attribution. Shared
queries are attributed once to the action that starts them, without multiplying
their query count by the number of waiting readers.

The same primary-process snapshots also include `queryOperations`: actual SQL
call counts partitioned by the existing innermost database-operation or request
route at `pg.Client.query` entry. Only a fixed allowlist of authentication,
workspace, Live ticket and list-read labels is retained; absent or unrecognized
contexts go into `unattributed`. Every snapshot and window delta must sum exactly
to its original `queryCalls`, and each bucket must remain monotonic. No query,
request, checkpoint or exclusion is added. These labels identify the operation
that issued a shared query, not every logical batch item that awaits it; connection
bytes are not allocated to individual operations. Historical reports without this
partition remain unavailable for this breakdown, rather than acquiring zeroes.

`unattributedSources` refines only that existing `unattributed` bucket. Its
test-only list names exact source-owned agent history, computer events,
conversations, pending actions, settings, device, daemon and background job
templates; `otherScoped` and `noScope` retain every remaining call without
exporting the underlying label. Its counts must sum to `queryOperations.unattributed`
at every snapshot and delta, while the original operation buckets and total stay
unchanged. Missing historical refinements are unavailable, and a mixed or invalid
partition fails validation. This diagnoses concurrent work without retaining SQL,
parameters, request data, arbitrary routes or identity values.

`rpcActions.queryDiagnostics` captures bounded, test-only metadata from the
first existing checkpoint; its per-query CPU and memory work happens inside
the measurement windows. After all existing measurements and cleanup, one
read of the isolated counter's
`/diagnostics` socket endpoint exports at most 8,192 query records in 2 MiB.
It leaves the original `/metrics` snapshots, windows and totals unchanged.
Each row contains the original cumulative query ordinal and indices into the
closed context, statement and scope tables. Contexts retain internal random
HTTP/item invocation IDs, method, route and action; they contain no user
identity, request arguments or headers. These IDs join the existing completion
receipts, including batch siblings with no SQL of their own.

Queries belong to `(before.queryCalls, after.queryCalls]`, even when their
request starts or finishes outside that window. An action unknown when SQL
starts stays unknown. Shared SQL belongs once to the context that issued it.
`normalizedStructureId` hashes a supported literal-free SQL shape; it is not
the production raw-text `mikka.db.statement_id`, and equal shapes do not prove
equal parameters or redundant work. Unsupported syntax, ambiguous contexts,
overflow and missing receipts remain explicit unknown or incomplete evidence.
The production request logger only registers a metadata getter; query capture
and export run exclusively in the isolated acceptance preload.

#### Native Codex request measurements

When daemon tracing and AI capture are enabled on Linux, each Codex child gets
one random-path loopback OTLP/HTTP JSON receiver. Its normal HOME, subscription
credentials and provider connection stay on the existing runtime path. The
receiver keeps only request ancestry, bounded model/conversation identifiers
and numeric measurements; native resource attributes, events, text, tool
arguments and errors are discarded. It accepts at most four connections,
1 MiB per batch and 4,096 pending records. It adds no database query or polling.

The child adds the receiver's `127.0.0.1` address to its existing proxy-bypass
lists, preserving the separate uppercase/lowercase values and all provider
proxy URLs. macOS and Windows currently retain app-server usage instead of
enabling native capture: Codex's optional system/PAC proxy policy can ignore
environment bypass lists. Telemetry never disables the user's provider proxy
policy to obtain native measurements.

For the pinned Codex 0.163 runtime, request identity is the native trace ID plus
the `try_run_sampling_request` span ID. `stream_request` and
`receiving_stream` must share that exact parent. Latency starts at
`stream_request` and ends at the `receiving` child of the completed response
handler. The enclosing request/stream spans can remain open while tools run,
so their end times and app-server notification arrival times are not used as
model latency. Native timestamps also position the APM generation span and
AI event independently of when an OTLP batch arrives.

`mikka.ai.timing_basis=official_cli_trace` identifies these native measurements.
`mikka.ai.ttft_basis=request_to_first_output_item` means time to the first
`output_item_added` receipt in the same request. This follows the official
[PostHog Responses SDK predicate](https://github.com/PostHog/posthog-js/blob/90e846aa04281713fb2d60e0afb88d6a1280c0ac/packages/ai/src/openai/utils.ts):
an output item can precede visible text. A `response.created` or `in_progress`
event does not establish TTFT. `mikka.ai.first_output_item_ms` retains the same
boundary explicitly. `mikka.ai.model_basis=native_sampling_config` identifies
the CLI's requested model; it is not a separate provider attestation of the
served model. The completed handler's closed reasoning-effort enum is retained
as `mikka.ai.effort` when supplied. This describes the native selected/default
configuration; the CLI can normalize or pin request effort, so this field is
not a separate wire-level or provider-served effort receipt.

Child shutdown starts a background drain within the daemon's existing shutdown
budget. Reordered batches and repeated exports are reconciled before emission.
Each successfully reconstructed native request consumes at most one matching
app-server usage receipt, matching conversation, model and all four numeric
token/cache fields as a multiset. Missing values remain distinct from zero.
An official completed response with all four usage attributes absent still
produces one generation from its proven request ancestry and native timing,
with token and cost fields absent. It does not consume a numeric app-server
receipt. A complete tuple takes precedence over an empty replay of the same
completion; partial or invalid tuples are not treated as absent usage.
Unmatched app-server receipts still produce generations with
`mikka.ai.timing_basis=app_server_usage`, without invented latency or TTFT.
The `daemon.ai.collection` span records native/fallback/matched counts,
`mikka.ai.missing_native`, incomplete requests, rejected batches, truncation
and whether CLI exit was observed. `mikka.ai.native_flush_confirmed=false`
remains explicit: observing process exit does not prove the native exporter
flushed every request. Check these fields in production alongside the actual
generation count; a successful run alone does not prove complete telemetry.
An incomplete native request is not automatically a failed generation: Codex
can preempt a stream without a completed response and still continue normally.
The existing run/adapter/provider error spans retain proven failures; missing
native outcomes remain unknown instead of being inferred from timing alone.

## Sampling and cost

- Critical Coordinator/dispatch/run/Workflow paths are retained at 100%.
  Ordinary traffic uses `MIKKA_TRACE_SAMPLE_RATE` (0–1), default `0.1`; an
  arbitrary remote caller cannot force retention through the sampled flag.
- Ordinary noncritical requests are recorded locally until their local tree
  ends. Errors, HTTP failures and requests at least 1000 ms are promoted with
  `mikka.trace.retention=error_or_slow` and `mikka.trace.sample_rate=1`.
  This includes requests selected by the initial head sample, so all retained
  failures use their effective rate of 1. A critical child also retains its
  buffered ordinary parent tree with `mikka.trace.retention=critical_child`.
  This local tail buffer is bounded to 256 concurrent traces and 512 spans per
  trace. Critical traces bypass it. These limits bound memory but can truncate
  ordinary traces under overload; the production acceptance must verify a
  controlled failure and a critical run, not infer coverage from configuration.
- `0` or a missing PostHog project token turns tracing off: no provider is
  registered. `NODE_ENV=test` and CI without `VERCEL` force the rate to 0;
  the historical `NEXT_PHASE=phase-production-build` guard does too. Nitro
  compilation emits the tracing entry; initialization happens when that runtime
  entry loads. Set `1` locally to see every request.
- Batch span processor (5 s, 512 spans per export, queue of 2048, then
  dropped). On Vercel a flush is handed to `waitUntil` when a request's root
  span ends, after the response.
- Exporting never blocks or fails a request. A failed export drops its spans
  and pauses exporting for a minute; there are no retries beyond the
  exporter's own bounded 5 s attempt.
- The tracer makes no database queries and does not change SQL (no
  sqlcommenter), so `pg_stat_statements` groups as before.

## Privacy

Enforced in `lib/tracing/sanitize.ts` on every span before export, and tested
in `lib/tracing/tracing.test.ts` with the real `pg` driver and instrumentation.

- No SQL parameter values: `enhancedDatabaseReporting` is off, and literals in
  the SQL text are replaced by `?`. No row content.
- Only allowlisted attribute keys leave the process; connection strings, users,
  hosts, client addresses and user agents are dropped.
- Query strings and fragments are removed from URLs, paths and span names.
- Emails and IP addresses in any kept string become `[email]` / `[ip]`.
- Exception messages, stack traces and status messages are dropped (database
  errors echo values); only the exception type is kept.
- Correlation uses bounded opaque `mikka.run_id`, `mikka.thread_id`,
  `mikka.task_id`, `mikka.task_number`, `mikka.workflow_run_id`,
  `posthogDistinctId` and `sessionId`; they identify telemetry, never authorize
  a request. Emails, IPs, credential-like values and free-form strings are
  rejected. Session Replay masks all text, inputs and element attributes and
  blocks media, canvas, iframes and editable content.

Adding an attribute means adding its key to the allowlist in `sanitize.ts`
and a case to the privacy test.
