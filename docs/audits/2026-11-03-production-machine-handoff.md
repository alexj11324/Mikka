## Confirmed request-authority blocker

Occurrence 10 × impact 9 = **90**. Completion runs inside the authenticated device database scope. The post-commit Factory callback parked the completed worker and revoked that same device token, then attempted to provision the independent stage inside the now-revoked request scope. The task/next run had already committed, so review remained queued. The old fixture called `persistRunCompletion` without the device authority scope; adding the real scope reproduces `Device authority revoked` before the fix.

The request now only enqueues `factoryCloudStageHandoff`. Its durable host step, in a separate invocation, validates the owned current Factory attempt/workspace and completed source before parking and starting. It never inherits the completed device token. Existing revocation checks remain intact; foreign owners and mismatched source runs are refused. Tests invoke the production workflow enqueue under both statement and unit fences, then execute the host step separately and verify source-token revocation plus placement on the dedicated thread device. No real E2B provider calls or workflow queue are used by those database fixtures.

## Additional confirmed machine-ownership regressions

Occurrence 6 × impact 9 = **54**. Both the Factory completion hook and the independent machine lifecycle can park the same finished run. Previously each read the machine without a lock, performed the external pause, and only then opened a transaction. Both could read `running`; a late caller could pause the sandbox after another caller had parked it and the next stage adopted/resumed it. Its unconditional device-token revocation could revoke the next stage's credentials too. The provider state and running review are consistent with this race; no historical per-call trace is available to identify which callback paused last.

The deterministic isolated PostgreSQL regression holds the first provider pause and starts the second callback. Before the fix, both call the physical provider (`2 != 1`). Parking now locks the parent run and machine in the existing provisioning/end order before reading state and retains the locks across tail capture, provider pause and token revocation. Adoption waits on that machine lock. A second callback observes the completed park; a callback for an adopted old run exits without provider calls or token revocation. Tail writes use the same transaction to avoid blocking on our own lock.

A related confirmed path (occurrence 4 × impact 9 = **36**) was that ending the old, already-adopted stage revoked the shared device's new token and retired the device. Its row retained the historical device ID but no longer owned a sandbox. A second regression reproduces that token revocation before the fix. End now changes device authority only while the row owns a sandbox or an in-flight creation.

The targeted real-PG lifecycle/stop suites pass all 23 tests after the fix, including refused pauses, sandbox adoption, stale callback token preservation and end/provision fencing. Type checking and targeted lint pass. The provider boundary is injected in those database tests; a fresh production full-flow verification is still required after deployment. Worker source and the measured templates do not change.
