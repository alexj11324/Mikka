## One durable path

Human POST with stable clientMessageId commits one root/key and responder work in one transaction. Changed payload under the same key returns409; omission of the key means a new logical message, not deduplication by text. Explicit mentions or an explicitly configured Lead produce durable work. Lead is set through the existing authorized review endpoint (`action:lead, agentId`, owner only, null clears); unavailable implicit Lead preserves the human message without executing. There is no implicit provider routing call. Role-based decision routing remains unavailable until separately configured; this candidate does not claim166's model-selection behavior. Correction records are retained using the existing correctionFrom policy for later authorized routing context.

Only conversation_work→session mailbox→dedicated group worker publishes replies. Do not also import166's processGroupTurn, groupRuntime.generate or message-route after() dispatcher. A source regression guard rejects reintroducing that path. Adaptation preserves explicit Lead, correction persistence, serial responders, prior group replies as untrusted context, no-add suppression and at most3 rounds. Agent output nominates followup IDs; server validates current grants, requester epoch and membership before enqueue. Work is unique by(root,Agent,round); each such intent publishes at most one reply. Multiple intentional rounds are distinct intents. Artifact revisions do not fan out and retain exact-version approval semantics.

Readiness is filtered before poll LIMIT and rechecked under the conversation transaction. A blocked group cannot starve unrelated groups. Existing work projects onto the same group_review run/mailbox; no duplicate group_chat status run is created. No private history, standing instructions, repository or credentials are added to context.

## External uncertainty and reconciliation

Database transactions and result hashes enforce at-most-once publication per intent, not exactly-once provider execution. An expired running lease becomes uncertain, never automatically reclaimed/reinvoked. Authorized `action:work` derives uncertainty even if the device never reconnects. Terminal replay with the same result returns the stored reply; a different result returns409. A completion connection failure is not converted into processor failure by the daemon. Its persisted status can be reconciled via `action:work`; only the requester/group owner can `action:reconcile, workId, decision:abandon`, which audits the decision and cancels the uncertain work. No automatic retry or privileged output recovery is implied. For a new authorized attempt the human must send a new logical request. Lost output before server commit cannot be reconstructed, and external execution may have occurred even if no reply was committed.
