# Deliver independent changes without an artificial batch dependency

- Date: 2026-11-20
- Source: Alex's [#2984 execution rules](https://github.com/alexj11324/Mikka/issues/2984), especially E and rules 3.1/3.4.
- Status: validated for adoption; effective with #2992's reviewed normal merge. The measured results below establish the policy; this status does not close the separate #2984 work items.
- Scope: future default development and delivery policy. Approved in-flight epic batches, including #2891 and #2956, retain their original rules and owners.
- Current procedure: [development workflow § 5](../../dev-workflow.md#5-ownership-and-merging). This decision records its reason, not a second checklist.

## Observed problem

The standing process combined any two ready PRs owned by one agent into a new
batch, even when they changed separate behavior. This adds a new integration
candidate and another validation round without establishing a real atomic
dependency. Existing documents also contradicted each other: CONTRIBUTING
required a normal merge commit while the development workflow permitted a
single PR to be squash-merged.

The #2984 investigation records original PRs, source SHAs, run attempts and
jobs rather than inferring durations from commit age. Its initial independent
repairs use different existing entry points:

| Change | Existing entry point | Why it can ship independently |
| --- | --- | --- |
| [Analytics summary allocation #2986](https://github.com/alexj11324/Mikka/pull/2986) | Existing reusable Analytics workflow and parent required gate | Changes scheduling and check attribution, retaining all actual build and browser commands |
| [Local bootstrap migrations #2987](https://github.com/alexj11324/Mikka/pull/2987) | Existing bootstrap and idempotent database setup | Removes a stale readiness cache; no workflow or product dependency on the other changes |
| [Attempt timing #2988](https://github.com/alexj11324/Mikka/pull/2988) | Existing completed-run collector and gate summary | Corrects read-only measurement; cannot authorize a merge or deployment |

The two original Analytics samples contain an extra 489 and 587 seconds
between actual regression completion and its separate summary completion.
Those are observed check delays, not a claim that whole CI becomes that much
faster. The bootstrap counterexample shows that a real helper change can
leave its old readiness stamp unchanged. Entering the existing setup instead
takes 1.916943 and 1.751009 seconds in two warm PG17 samples while preserving
all 396 recorded migrations and their timestamps. Exact merged PG17 warm runs
were1.627864 and1.851708 seconds, with the same ledger and timestamps; this
reliability repair deliberately pays that measured setup cost. The timing collector's two
real retry counterexamples establish why time before a retry and successful
work retained from a previous attempt must be reported separately.

## Decision

Use the smallest independently safe and verifiable change as the default
delivery unit. Keep recovery branches and Draft PRs. After focused debugging,
complete the original full `pnpm check` and applicable local acceptance on the
committed candidate, verify the existing exact-source local-ready evidence,
then mark it Ready promptly. Merge with a normal merge commit
after review, all applicable protected checks and the current release window.
Do not make another unrelated PR or a batch size a prerequisite.

Use a batch only when intermediate states would violate a concrete contract,
such as mutually dependent protocol/schema consumers. Record that dependency,
preserve each original owner, integrate with normal merges and validate the
final candidate. Already approved epic-specific batching remains effective;
this decision does not rewrite another owner's plan or take their work.

Retain valid results only when the tested source, dependencies, toolchain,
fixtures and relevant environment still match. GitHub's native job retries,
PR/commit check association and the existing immutable service receipts own
reuse. Diagnose the failed stage before rerunning; never add a second poller,
status writer, result cache or scheduler. Reuse also requires surviving
prerequisites and the owning workflow's recovery contract; E2B cleanup destroys
failed candidates, so its replacement run must recreate them. A build result does not replace a
security, migration, runtime or deployment acceptance contract.

The separately owned, already merged #2997/#2998 local-first policy remains
in force: ordinary source/runtime failures are diagnosed in the task's cloud
Linux environment; Draft checkpoints are durable recovery points. Their
required aggregate checks intentionally fail, while expensive selected jobs
wait until Ready. Final CI independently verifies a completed candidate.
This delivery decision does not change that policy or count a Draft failure
as a product regression.

After merging, verify the actual merge SHA, its tree and the affected behavior.
Record code delivery separately from release acceptance; use the existing
release owner's exact receipt for staging or production. Preserve #1752's
applicable release windows and #1954's sole production promotion authority.

## Validation and limits

The original samples and red/green regressions are linked in the three PRs.
Their final protected CI, Ready-to-Merge intervals, merge SHAs and exact
post-merge results are recorded in the [#2984 results](../../ci/2984-results.md).
The representative independent normal merges are603d1d95 (#2988),8cddaa7c
(#2987) and04036259 (#2986), with exact merged focused tests and successful
main CI. The later Site (#2993) and runtime-consumer (#2995) repairs are
additional deliveries, each with its own source-specific verification and
explicit limits. These observations establish feasibility, not an estimate
of the time an unexecuted combined batch would have taken. A missing accepted deployment or missing Ready event remains
unmeasured, never zero. Compare the actual workload and queued stages; do not
claim statistical or whole-project speedup from these small samples.

Changing the merge policy does not weaken any branch protection, safety scan,
assertion, timeout or migration gate. If an integration dependency appears,
validate the affected combination and use a justified atomic batch; do not
restore arbitrary batching for unrelated work.
