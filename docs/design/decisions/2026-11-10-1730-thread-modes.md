# A thread is Plan, Execute or Ask; the run freezes which

- Date: 2026-11-10
- Source: #1730 (Capy parity, Wave 3): a coding thread needs a mode the
  person can pick, and the mode must be enforced where tools run — never a
  UI label over a run that can still do anything.
- Rule: a thread has one mode — `plan`, `execute` or `ask`. The server stores
  the person's choice per task in `task_thread_modes`, and each admitted run
  freezes it in `agent_runs.mode`. A run's mode, policy and revision are one
  fence: a stale approval, a retry or another device cannot spend authority
  from a different mode.
- Reuses: the existing run policy (`workspace`, `worker`, `agent` and
  scope layers), the existing read-only policy (ADR 0046), and the existing
  run-bound tool-approval gate. No third permission system is added.

What follows:

- `plan` is the existing read-only policy applied to the run
  (`applyThreadMode`). The host tool paths refuse writes too: app tools deny a
  tool without `readOnlyHint`, custom MCP calls are refused, and the daemon
  gives Claude Code a read-only `canUseTool` allowlist and Codex its native
  `read-only` sandbox. A plan run has no task branch and publishes nothing.
- `execute` is the behavior a run had before modes existed. The policy is
  unchanged.
- `ask` keeps the policy, but every risky step waits for the person:
  Claude Code's `canUseTool` and Codex's native command/file-change/MCP
  approvals call the run-bound gate. Codex starts Ask in its read-only
  sandbox and asks for each untrusted command, so a write is requested
  instead of silently applied. The gate stores one exact request in
  `agent_tool_approvals`, waits for the owner's decision and consumes an
  approval exactly once. A decline, timeout, lost lease, changed mode or
  changed policy is never an allow. App writes already use their existing
  approval card; ask mode makes every app write take that path.
- The API is `GET/POST /api/threads/:runId/mode` (the run names the thread;
  the response carries `mode`, `version` and the run's frozen `mode`) and
  `GET /api/runs/:runId/tool-approvals` plus
  `POST /api/runs/:runId/tool-approvals/:approvalId` for decisions. A
  transition carries `expectedVersion`; a stale picker changes nothing.
- A transition is refused while the thread has an unfinished run
  (`threadModeLocked`). The active run keeps the mode it froze; the person
  changes the mode after it ends and the next run inherits it. A replay is
  checked before the freeze, so a late idempotent retry cannot revert a newer
  choice. Retries, quota continuations, question continuations and cloud
  recovery copies carry the source run's frozen mode; none may fall back to
  Execute by inserting a run without one.
- Advertised capability is honest: a daemon without `threadModes` is served
  Execute only; a harness without native ask support (Cursor, mock) is
  refused with `threadModeUnsupported` at claim instead of running ask
  without enforcement. The daemon reports `threadModes` only where its live
  gate exists.

Cost if wrong: a thread cannot switch mode mid-run; the person restarts the
next run to change it. Custom MCP calls are unavailable in Ask (the server
cannot hand that remote effect to the run's approval gate) and are refused
rather than run unapproved.
