# 自动化第一版：范围和 dispatch_task 的授权

Alex，2026-11-15：参照 Capy 的 Automations 做「自动化」页面和编辑页，第一版只支持「定时」和「手动运行」，执行内容是「交给某个 Bot 新建任务并派发」。只学 Capy 的布局和交互，不用它的代码、头像和文案。

## 决定

**范围**

- 触发条件只有两种，编辑页写「满足任一条件就运行」：定时（一次、每隔、每天、cron）和手动运行（立即运行）。每天的时间遇到夏令时重复的一小时，由用户选较早或较晚，不替用户默认。
- 执行内容只有 `dispatch_task`：把一句要求交给一个 Bot（不选就是 Coordinator），新建任务并派发；可选标题、机器和 Agent 配置。
- 页面的读写都走 `executeScheduleCommand`，不另写存储或授权；数据更新走 live 通道（`schedule_list`），不加轮询。
- 不在第一版：GitHub、Slack、Linear 事件触发（`app/api/webhooks/*` 已能接收，未接到自动化）；每个自动化专属的 webhook 地址（只显示一次、可更换、按时间窗合并事件）；模板；运行次数和花费上限；Slack 发帖选项。

**dispatch_task 的授权**

- 以创建者身份运行：每次触发都走创建者自己的「创建并派发」路径（同一个任务命令、同一个 `createIssueFromRequest`），用这次触发的 ID 做请求 ID，重试不会建出第二个任务。
- 每次触发都重新检查：创建者仍是 active 成员、Bot 还属于他且没归档、Bot 的仓库在工作区里仍可用、选的机器和 Agent 配置仍可用。检查失败就记一次失败并报告原因，不静默跳过。
- 建出的任务和普通任务权限一样，Secret 的暴露范围也一样，不放宽任何东西；它和 `agent_read` 的「只读、禁止对外写」是两回事。Bot 收到的请求标明来自用户的自动化，不代表用户的额外批准。
- 页面上的操作由登录的本人发起（没有对话里的源消息），权限规则不变：成员可以查看、暂停、删除；只有创建者或 owner/admin 能修改、恢复、立即运行。
