# 任务页：按职责拆开，把唯一的动作放进表头，把状态画出来

2026-11-18。Alex 在「非常潦草」之后逐面修，PR 面（[2026-11-18-1400](2026-11-18-1400-pr-surface-and-craft-baseline.md)）之后，crew 把任务页排在第一。

任务是官方界面里 Alex 每天待得最久的一页，也是最后一个「一个文件干很多件事」的文件：`mikka-hosted-ui/slots/task-detail.tsx` 908 行加一段 207 行的 CSS 字符串，PR 列表在 #2831 之前就是这个形状。它的**排列**在 2026-11-14 已经由 Alex 定过（[2026-11-14-2330](2026-11-14-2330-capy-activity-and-thread-titles.md)）：属性从右侧卡片挪到标题下的一列，照 Capy 的 issue 页，描述与活动仍是一页往下读。所以这一页的问题不是排列，是**没人从文件结构上认识它**，以及**该画的状态没画**。

## 决定

- **按职责拆文件，一文件一件事。** `components/mikka/task-detail/` 下 frame（表头、正文栅格、右栏）、identity（标题与编号行）、properties（属性列）、description、subtasks、activity、marks（字形与菜单）、styles；`slots/task-detail.tsx` 只把槽指向它。这与 PR 面 #2831 的做法一致，也是 review-page 已有的目录形状。
- **2026-11-14 的排列不动。** 属性仍在标题下一列、描述与活动仍在一页往下读。brief 里「右侧属性栏」「换成概览/改动视图」是 PR 面的词汇（那份 brief 自己写的是 overview / changes / checks），用在这一页会推翻 Alex 对**这一页**的决定，所以不采用，并在此说明。
- **表头有且只有一个主操作：任务自己的线程。** 工作不在这一页，Alex 要的是「这件事到哪了、要不要我」，所以去线程是唯一值得占表头的位置；`⋯` 里仍是设置类的次要动作（R-91）。
- **状态画出来而不是默认。** 加载态是同一页面的形状；「还没有活动」与「没有符合筛选条件的活动」是两个状态；不可用/已删除仍是一句状态加一个动作（R-41）。
- **计数放在名字旁边，不放说明。** 「活动 4」是一个数，不是一句「共 4 条活动」（R-40）。

## 实现

- 公开仓库：`components/workspace/task-detail.tsx` 的加载分支换成 `TaskDetailSkeleton`（48px 条 + 680px 阅读列，属性行与真实行同高）；`messages/{zh-CN,en}.json` 各加两条状态文案。
- 私有仓库：上面七个文件，加 `slots/task-detail.tsx` 的 6 行入口。
- 没有新增组件库里的一份：属性列、子任务、活动都是原组件按原样组合，改的是密度、占位与状态。页面自己的加载骨架是这一页的形状，不进 `components.md` 的组件表。
- 付费块未动：`components/agent-thread.tsx` 与 `patches/` 都没有改。

## 没有做的

- **「机器已回收」这个状态没有画**，因为这一页拿不到它的数据：`TaskDetailFrameProps` 里没有线程的运行错误，`agentActivity.failed` 是一次**读取**失败而不是运行结果。这个状态现在由「对话」属性行里的运行结果词显示（`RunErrors.workspace_machine_unavailable`），要单独画成块得先给契约加一个字段，那是另一件事。
- 不改宿主层 token，不改付费 Thread 的外观，不动任务状态图标（MIKK-55 的例外）。
- 任务的标题字重从 500 到 600 会让长标题略宽，这是 R-32 的取值；如果 Alex 觉得重，改的是 R-32 不是这一页。
