## Completed backend behavior

The owner/revision transaction records `scopeSetBy=user`, restores the existing personal identifier and writes one activity version. A monotonically increasing `scopeVersion` changes on every actual scope transition. Personal retirement atomically saves remote identity tombstones, retires publications, removes active sync mappings, finishes old outbox jobs, cancels nonowner runs, clears leases and revokes tokens. Current task visibility also applies to a member's own runs.

A publication reserves its stable remote UUID in a committed transaction **before** HTTP, using an existing owner-matching verified link. The current policy never infers an external target for a new task or a personal-to-team conversion. A verified legacy import can retain its remote identity and generation on retry. The database makes publication identities immutable and forbids reactivation of retired identities.

```text
workspace v1 / verified remote A -> personal v2 / A retired
                                -> explicitly chosen Mikka team v3 / Linear blocked
```

Writers serialize per publication through a dedicated, short-lived PG advisory-lock connection. No task row or publication transaction is held across issue/comment HTTP, so retirement can commit while an old response is still delayed. Credential-refresh behavior is unchanged. The writer takes a fresh snapshot in its captured generation after acquiring its publication lock. Each issue/label/comment mutation rechecks generation/claim ownership; local acknowledgements and mappings recheck under the task row lock. Comments retain their captured publication link rather than looking up a possibly newer link by local task ID. An unacknowledged write is recorded so a reclaimed claim does not interpret the application's own delayed write as a new remote edit.

Outbox jobs capture `scopeVersion` and receive a new claim token on each claim. Success/failure updates require that exact processing claim; retired jobs cannot requeue themselves or overwrite a new link/job/diagnostic. Old webhooks stop before provider access when already retired, and revalidate generation before changing diagnostics when retirement happened during HTTP. Imports resolve a reserved remote UUID back to its original local task rather than creating a second task.

An in-flight operation that passed its last check may still reach or finish at **retired remote A**, using its captured workspace content. Its result cannot attach to personal state or to the later local team state, and it never reads newly personal content. No archive, delete or unlink provider policy is inferred from this fact. Guard-only tombstones for a legacy app UUID are not evidence that a real remote issue exists to archive.

## Run completion revocation fix

The reported `/complete` race was reproduced on a task with **no Linear link or queued sync**: a request paused after reading a live run subsequently changed a personal task to review. The retained pre-fix PG record is `status=review, scope=personal`.

`lib/run-completion.ts` now locks task then run, rereads permissions/live state, and commits run terminal state, token revocation, completion event and permitted review mutation together. A separate short task lock rechecks scope/generation before scheduling postcommit dispatch. Retirement winning first causes zero run/task/event writes and zero dispatch; completion winning first commits before retirement, and its deferred dispatch is rejected after retirement or a personal-to-workspace round trip. Deadlock/serialization retries apply only to rolled-back local transactions, at most twice. An independent read-only investigation/review was reconciled, including a real heartbeat deadlock reproduction and retry fix.

Legitimate owner-personal and null-task completions, member completion while workspace, plan behavior, `not_run`, failed verify, and terminal replay remain covered. Coordinator and worker-auth helper logic was not changed.

## Public retry generation regression

The independent review reproduced a P2 regression at `38ee473`: after the ordinary public personal-to-workspace action creates generation 2 and its initial job is done, `retryLinearIssue` inserted a new job with the database default generation 1. The worker made no provider request, marked it done and left the link pending. The retained pre-fix run asserts `1 !== 2`; the normal forward action itself succeeds as a control.

The public retry now takes the task row lock, rechecks owner/current workspace/deletion state, and captures the current generation in that transaction. It restarts failed jobs only in that generation, clears their claim, and inserts explicit generation for new work. Stale open jobs are finished without retagging their identity; old failed jobs remain retained. The task lock serializes retries without taking the old issue-ID advisory lock in the reverse order from imports. A retry that waited for retirement returns an error without enqueue or dispatch. A retry that waited for retirement is rejected. A later explicit Mikka team promotion stays provider-blocked; it cannot create a fresh remote UUID.

Both public actions execute with the actual Next `AfterContext` lifecycle in the real PG suite; their scheduled worker callbacks run after the action. The regression asserts queued generation before response close, provider HTTP after close, and final synced link/done job. It also covers restarting a current-generation failed job and preserving old-generation failed/processing identities.

The conservative public personal gate now checks **any retained publication** and **failed outbox jobs**, as well as links and queued/processing work. A real loopback sequence makes seven transport failures, then succeeds remotely on attempt eight while losing both response and fallback lookup. With no link and an exhausted failed job, the action stays blocked with unchanged scope/revision and zero additional provider calls. A reservation still blocks after its job becomes terminal; a failed job without a reservation also blocks. Absence of a link or a terminal job is not proof that an external issue does not exist. These are policy guards, not authorization to archive.

## Explicit team creation

`createIssueForTeam({ requestId, teamId, title, content, status, priority })` is an owner-session server action under the `/mikka` Next application. `requestId` and `teamId` are UUIDs; the caller must retain the same request ID and identical request body on retry. Success returns `{ issue, linearSync: { enabled: false, reason: 'no_explicit_target' } }`. On first completion the task has `scope=workspace` and `linearSyncBlocked=true`. A later replay returns the task’s current scope and does not re-promote it. This is a persistent per-task gate: enqueue, manual retry, publication reservation and Linear link insertion cannot publish it. Other tasks and the user's global Linear configuration are unchanged. A later verified external target association is separate work and is not implemented here.

The action checks active workspace membership for the selected team, using the existing access model (it does not introduce a separate team-member ACL), creates the task personal with the block already set, commits its team association and durable workspace receipt, then rechecks the membership and exact association under workspace locks while committing the scope change in the application database. A request row and payload fingerprint prevent duplicate or altered replays. A retained receipt prevents retries from restoring a team relation that was changed or removed later. Failure before promotion leaves a personal task; a retry can complete it without duplication. If a commit response is lost, the action reconciles its request record; if reconciliation is unavailable, it returns `teamIssueOutcomeUnknown` and the client must retry the same request ID rather than assume either outcome.

Errors are `teamIssueInvalid`, `teamIssueAccessDenied`, `teamIssueRequestConflict`, `teamIssueChanged`, `teamIssueRetry`, or `teamIssueOutcomeUnknown`; database-stage errors include `requestId`. Any internal `actAs` context, including one without an explicit actor, is rejected by this user-choice action; it requires the ordinary signed-in session path. The existing UI's two-call `saveIssue`/`setIssueTeam` flow is not equivalent; frontend integration must call the new action. The legacy `setIssueScope` workspace path is now rejected with `issueScopeTeamRequired`, since it has no target. New explicit team creation uses the team action. `promoteIssueToTeam({ requestId, issueId, revision, teamId, expectedTeamId })` provides the equivalent locked protocol for an existing personal task without creating a copy. The UUID request binds the task revision and current team snapshot; success retains task identity/content/owner and returns the same blocked sync state. The current team snapshot is the successful `string | null` result of `getIssueTeam(issueId)`; pending/error is not null. Completed requests return current state and never restore a subsequently changed or removed relation. Missing authentication from the team, preview, and confirmation actions is returned as `authRequired` through the shared action boundary; unexpected errors still propagate. On a completed request replay, `issue` is current state and can already be personal; it is not promoted again.

A new pending migration `20261026224200_require_verified_team_promotion.sql` fences every personal-to-workspace update: the task must be provider-blocked, carry user scope attribution, have the matching pending team request, and have task/team transaction-local markers installed by the server while its workspace membership and relation locks are held. An old scope-only writer or a lone marker without a request is rejected. Existing Linear-origin workspace inserts and already-workspace publications are not detached. The task/team markers are an assertion by trusted application DB code, not proof against a principal with arbitrary SQL write access.

The local candidate also introduces `linear_issue_links.externalTargetVerified`. Publication and per-issue dispatch require this marker and an owner-matching link; an account-level active Linear team or an unacknowledged publication is insufficient. New authenticated Linear-origin imports mark their own links verified. The candidate migration backfills only links whose local task ID matches the remote ID and whose revision-one history proves a system Linear import. Other legacy links are retained but their inbound content/removal/diagnostic updates and outbound sync pause until a future explicit verification flow; this may pause some previously authorized links whose provenance is unavailable. The migration and compatibility impact require review and have not been exercised against PostgreSQL under the current retention restriction. In-flight external calls from older binaries cannot be recalled; rollout must account for older workers.

The prior DB suite's automatic Linear republication expectations have been replaced to match the user's explicit-team rule. The suite retains delayed old updates/failures/webhooks, old claim replay, content/comment edits and retries across retirement and explicit local team promotion, and now requires zero new external publication. Verified imports keep their ordinary synchronization and retry positive controls. A synthetic legacy generation-2 import and unlinked failed job are reconstructed by replaying tracked migrations 2240, 2242 and 2243 in the fresh scope database; the last replay restores the final scope gate. No fixture directly sets the verified flag. This validates migration compatibility against synthetic provenance, not the existence of a real historical state or real provider acceptance. Additional prepared tests cover verified remote removal, removal waiting for retirement, personal UUID collisions, blocked reservations and new remote imports. These PG/HTTP tests remain unexecuted under the retention restriction.

The regression uses two separate retained PG17 databases and actual server-action calls, plus synthetic loopback HTTP. It covers simultaneous replay, unauthorized and agent attempts, first application transaction failure, association failure, promotion failure, changed association, and membership revocation between commits. Tests also update task/document state, attempt direct outbox/link writes and manual retry, and verify no provider request or outbox for the blocked task. No production migration or real Linear write was performed. The HTTP harness invokes the action; it is not a frozen deployed Preview.
