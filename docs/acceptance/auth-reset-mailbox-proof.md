# Password recovery and automatic social linking

A successful email password reset now also verifies the exact mailbox to which Mikka issued the reset link. Mikka stores only a hash-indexed binding of the reset token to user ID, email and expiry. Better Auth 1.7.12 consumes that proof and the reset token in the same PostgreSQL transaction as verification, password replacement and session revocation. An email change, expired/missing proof, failed credential write or replay cannot publish verification.

Google/GitHub linking stays automatic for an existing verified local email and a verified matching provider email. `trustedProviders` remains empty and `requireLocalEmailVerified` retains its safe default. No manual settings linking step is required for that path. GitHub uses the authenticated `/user/emails` verified primary address, never a public/non-primary profile address; a missing/unverified primary email safely rejects the callback.

Previously consumed reset tokens cannot be used as retrospective proof. Neither credential timestamps nor an empty session list prove mailbox control. Historical unverified accounts retain their current password and need the normal verification-email flow once. Reset links issued before this binding was deployed lack proof and must be requested again; their lifetime is at most 15 minutes. No migration or manual account update is required or performed.

Validation uses isolated PostgreSQL and the actual Better Auth HTTP handlers/callback/state processing, with only external OAuth exchange/profile and mail transports replaced by synthetic fixtures. Cases include successful reset, expiry/replay, missing proof, changed/deleted/recreated owner, concurrent email change, failed credential write rollback, normal Google/GitHub implicit linking, unverified identities, existing provider subject ownership, and the actual GitHub reader. These tests do not claim real provider consent, deployment, or user account acceptance.
