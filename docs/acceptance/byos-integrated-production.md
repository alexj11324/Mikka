# Integrated BYOS backend candidate

Base: PR254 c7a017a9 (including reviewed group/lease/Skill/credential integration), plus PR253 275fee68 mailbox-proof recovery. BYOS source: PR206 9e610781, excluding its obsolete auth changes and settings UI. This candidate does not activate a route, move a real grant, create IAM, run production migrations or replace a live deployment.

Existing claim functions remain authoritative. BYOS binding insertion shares the ordinary execution and Factory check claim transaction; cancellation and stale connection revision refuse the claim. Question continuations requiring a prior session remain supported for existing local adapters, but hosted BYOS cross-run continuation is explicitly refused before any launch because its isolated runtime cannot yet prove the prior-session continuation. A new fresh session must never substitute silently.

## Service authentication

Use `MIKKA_BYOS_VAULT_AUTH=universal`; server receives distinct `MIKKA_BYOS_CUSTODY_CLIENT_ID/CLIENT_SECRET` and `MIKKA_BYOS_ACCESS_CLIENT_ID/CLIENT_SECRET`. Keep explicit `MIKKA_BYOS_INFISICAL_ORIGIN=https://app.infisical.com`, the already verified project origin. Do not redirect or silently switch hosts. Existing project/environment/path variables still fix each store. Runtime no longer loads legacy static admin tokens. Enrollment remains custody-only; reader setup is not a prerequisite to receiving consent.

Reuse PR254's Universal Auth token cache, not its cleanup identity or permissions. Require335s remaining validity before each worker dispatch (275s maximum request plus55s bounded publication/termination and5s margin). Proposed600s tokens refresh early enough for that bounded worker; every subsequent request resolves the current role's lease again. Failed authentication never falls back to a static token. Worker processes receive only the selected short-lived token through stdin, never client secrets; executionOnly workers receive no full-grant token/path. Native CLI continues to use the external broker rather than subscription bearer values. Provider refresh tokens remain in custody. Bootstrap-client-secret rotation is operational work, not implemented token refresh.

## Retained staging grant and production destination

`subscription-transfer-contract.ts` validates a short-lived explicit approval envelope bound to enrollment, source digest/revision/provider subject, authenticated app owner/workspace, exact production origin/database identity and exact source/destination stores. It contains no credential values and rejects source deletion permission. This is an approval contract only, NOT a live transfer executor or one-use journal. The existing binder handles same-environment escrow publication with durable ownership fences. A cross-environment executor must additionally lock the source revision, atomically reserve its one-use transfer journal, publish create-only into the approved destination, verify integrity and commit the normal authenticated binding; failures must preserve the sole grant. It must never expose a bundle to browser/chat or silently fall back to fresh consent. Current single-environment configuration cannot execute a staging-to-prod transfer. No claim of completed production grant migration.
