# Personal approved-write endpoint

Depends on the transaction foundation in PR373. The endpoint POST `/api/approved-writes` (normal app base path applies), Coordinator tool registry and owner/session approval services share one operation ledger. The feature does not replace existing email/calendar-create/update handlers. Availability defaults on in every deployment scope. The optional server-owned `MIKKA_PERSONAL_WRITES_ENABLED=0` remains an incident kill switch; any explicit value other than `1` closes admission. Request input cannot override it. Disabled calls return 503/approvedWritesDisabled before auth, application Pool or provider runtime loads. Availability grants no provider permission and does not expand existing frozen tool snapshots.

## Existing-schema compatibility

No ordinary Drizzle schema/table definition changes. Existing `db.select().from(pendingActions)` therefore still projects only its historical columns. Deployment applies four additive migration sources before serving the feature; unchanged legacy paths do not need them:

- 20261028143920_operation_ledger.sql: generic execution ledger, bound to owner+personal workspace+persisted proposal ID.
- 20261028143921_approved_write_binding.sql: ledger invokedAt plus pending_actions intentKey/operationBinding and owner+intent uniqueness. No new Drizzle columns on pendingActions. Historical308 names are recognized only with exact SQL hash matches, avoiding automatic replay of old applied payloads.
- 20261029043646_agent_external_write_policy.sql and 20261029043647_workspace_external_write_policy.sql: external-action decisions and independent revisions on existing agent and workspace policy records. These are the current main filenames; historical names are handled only by the existing migration-history checks.

There is no separate Coordinator receipt or approval table. Coordinator tools use the existing pending action and operation ledger; native calls reuse the existing native scope fence. A required CI-only real-PG regression creates a fresh legacy-only schema, applies only the frozen old pending_actions DDL, inserts one synthetic pending email, calls the actual legacy list for owner/other-owner, and calls the actual disabled product POST. It asserts the new columns/tables are absent. The fixture refuses non-Actions/non-CI/non-required mode, other DB URLs and non-PG17. Hard caps:40query dispatches,3DDL statements,1INSERT,0UPDATE/DELETE/DROP/auth/provider. Only the ephemeral Actions mikka_e2e service at127.0.0.1:5432 is permitted; unique fixture schema and data remain until that service exits. No retained local DB is used. ## Browser contract

When deployment configuration admits the service, accept only POST, exact same Origin and browser cookie, with no Authorization header. Better Auth resolves the owner/session server-side with cookie cache disabled; session expiry/revocation is rechecked in the database. Model text, user-supplied owner/connection/workspace fields and displayed proposal cards are not approval.

- Propose: `{op:"propose",action,input,intentId:UUID}`. Create an ID for one explicit human intent, retain across HTTP/lost-response retries and409/503; explicit new intent gets a new ID. UUID case is canonicalized. First read replay under the intent lock, resolve metadata with no APP transaction open, then lock/re-read/limit/session-check and insert. Concurrent metadata reads may duplicate, but the committed intent has one proposal. Changed action/payload rejects, never silently selects a new ID.
- View: `{op:"view",action,id}`. Returns frozen input, approvalContext, account `{provider,accountId,version}`, timestamps, status and error. No approval, effect, provider lookup or projection writeback.
- List: `{op:"list",limit?:1..50,cursor?:string}` (default20), returns `{items,nextCursor,asOf}`. Fixed-asOf descending createdAt/id cursor is owner+session-bound. Consistent proposal/ledger snapshot per page; status may advance between pages. Ambiguous/tampered legacy rows become attention-only and cannot poison the whole page or become approvable. Uses its own projection rather than the legacy filter which excludes new/running actions.
- Decide: `{op:"decide",action,id,approve:boolean}`. Explicit authenticated human approval only. Frozen owner/account/target/version/content is rechecked before send. Repeated confirms share the persisted operation ID and invoke gate; unknown outcomes never authorize resend or become declined/no-effect.

Supported actions: append_notion_paragraph `{page_id:UUID,text:1..2000}`, send_slack_message `{channel:C/G/D-ID,text:1..3000}`, and cancel_calendar_event `{event_id:1..1024,send_updates:"none"|"all"|"externalOnly"}`. Text is trimmed and unknown fields reject. Slack conversation facts are read through the account-pinned `conversations.info` proxy adapter; the stored local adapter contract version is not a provider API version. Calendar uses account-pinned conditional deletion with the event ETag. The model chooses the action and target; the adapter checks identity, input shape and provider evidence rather than restricting conversation or event categories.

HTTP400invalid envelope/input,401session/Bearer rejection,403Origin,409domain/uncertain COMMIT,503unavailable/disabled.200is a typed result, not automatic provider success. View/list statuses pending/running/done/declined; running+operationUncertain remains unresolved. COMMIT errors retain explicit committed/unconfirmed state from the foundation; clients keep IDs and inspect the same result. No automatic transaction-body retry.

## Default permission (2026-10-31, R-77)

Explicit `ask` and `deny` in the agent's or workspace's `external_write_permissions` still narrow, and an explicit `allow` runs without a model call. Only when no setting names the action (`lockWritePolicy` reports `defaulted`) does `proposeFromRun` ask the injected `judgeWrite` (`lib/operations/write-judgment.ts`, on the existing Decisions route via `decide`) one predicate, `destructive`. Its input is the action, the write tool's slug and Composio tags (the MCP hints, from `composioWriteProvider.prepare`, which already fetches the tool) and the concrete payload. Every call is judged, a `readOnlyHint` tool included (the hint is input); probability ≥ 0.5 (the existing predicate cut-off) asks; an unavailable, refused or malformed answer shows no card: the agent's own call goes ahead and the log records `Write judgment fallback` (decision 2026-11-01-1330). The result is frozen in `operationBinding.run.approvalDefault` and the ledger `policyScope`, so every later check (insert, decide, ledger phases) resolves the same way. Bindings made before this change keep `ask`. The Coordinator's Gmail/Calendar writes use the same judge in `writeAccountAction`.

## Product approval integration

The client first reads public GET `/api/approved-writes`, which returns only `{enabled:boolean}` with status 200 and `no-store`, using the same server-owned gate without loading auth, database or provider services. Until it reports exactly `true`, the client does not POST list/view requests or render retained uncertain cards. Stable disabled deployments therefore produce no repeated 503s. Availability grants no authority: every POST still checks the current gate, session and operation policy, and a disabled POST retains its 503 contract. There is no second `NEXT_PUBLIC` flag.

The existing approval area above the composer renders the new Notion, Slack and Calendar-delete proposals through `ApprovedWriteActions`. It uses only the authenticated `/api/approved-writes` list/view/decide path; the old mail/calendar-create/update list and decider remain separate. Cards retain the existing 14px approval-card layout (R-33), show frozen content, exact account and target, and expose explicit approve/decline controls. An expired proposal cannot be approved. Invalid bindings are attention-only and cannot be approved.

Discovery accepts optional `unresolvedOnly:true`: it excludes terminal history and successful ledger outcomes before pagination, so old pending requests cannot be buried behind completed actions. Cursor binding includes this filter. The default discovery mode is unchanged. The HTTP list returns the authenticated `viewerId` so a stale session hook cannot put another account's response under an old browser cache key. No owner/account authority is accepted from request JSON.

The new service being disabled yields no new cards and does not hide old approvals. Other load failures have a retry of the read only. A decision is sent once per explicit click. A lost/unconfirmed response keeps the exact action visible as `Result unconfirmed`, suppresses further approve/decline controls and polls the read-only view. If that authenticated view confirms the same action is still pending and unexpired, an explicit `Resume approval` control clears only the browser's uncertainty and refreshes reads. Approval or decline then requires another separate click. Running, unavailable and expired results cannot use this recovery path. A disappeared list row is not treated as proof that the action failed or succeeded.

Source/component tests cover all three ask proposals, frozen content/account, independent old/new routing, disabled-service compatibility, pagination, expiry, switched-cookie response rejection and lost-response behavior. They use synthetic HTTP/auth leaves and do not establish provider acceptance. This addition changes no feature flag, permission, grant, credential or migration.
