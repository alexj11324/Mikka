# Nontransactional migration prerequisite for #116

This replaces only the missing executor capability from closed #84. It preserves main's single `scripts/run-db-tests.mjs` runner (#171), opt-in `pnpm migrate`, code-only build, baseline ordering and exact-SQL ledger aliases. It does not implement #116, add SQL migrations, modify executed migration files or touch UI/auth paths. #116 still waits for this prerequisite to merge.

A leading comment header can declare `-- migrate: no-transaction`. Such a file contains exactly one statement sent unchanged in one query, outside any runner-created transaction. Separate validation files can therefore release the previous file's locks first. Normal SQL files retain existing whole-query execution (including any explicit transaction in their source). This is a conservative planner, not a SQL lexer: no-transaction files reject multiple statements, dollar syntax, transaction keywords, semicolons inside comments or strings and unsupported uses of CONCURRENTLY. Idempotency is the migration author's responsibility; the executor cannot prove arbitrary SQL is safe to replay. No new SQL is supplied here.

All plans are validated before any database connection. Concurrent index creation additionally checks `pg_index.indisvalid` before recording the migration. Failed/INVALID indexes never enter the ledger; an existing INVALID index is not accepted merely because IF NOT EXISTS succeeded. The runner gives a manual DROP INDEX CONCURRENTLY hint and never drops an index itself. Data/DDL and ledger recording remain separate; successful nontransactional DDL can survive a later ledger write failure, so a file must be replay-safe. Deployment runners must remain serialized; no global advisory lock or automatic retry is added.

Three immutable main migrations (`20261026013001`–`20261026013003`) already contain single CREATE INDEX CONCURRENTLY statements without the directive. A SHA256-bound compatibility inventory recognizes their exact original bytes and applies the same index-validity check. Their comments contain rollback semicolons, so the exact-byte compatibility path exempts only that legacy comment-count restriction; statement/transaction/CONCURRENTLY validation remains. Altered bytes lose the exemption. Existing executed SQL is never rewritten.

Validation includes pure planner/mode/ledger-order/inventory tests; all 64 current tracked SQL files preflight. The new required database suite goes through #171's runner and independently refuses execution unless GitHub Actions, the exact loopback `mikka_e2e` URLs and PG17 are present. It tests actual concurrent success, failed unique-index INVALID state, IF NOT EXISTS retry rejection, manual cleanup and successful recovery, ordinary multi-statement rollback, and separate ADD NOT VALID / VALIDATE statements. Local DB execution is prohibited. The standard CI empty-database bootstrap also exercises all current historical SQL and rerun behavior.

The candidate branch excludes only its own live Infisical/provider-credential job. Strict policy/types/lint, existing ephemeral DB gates and production build remain unchanged. No real credential lookup, production migration, deployment or merge is authorized by this change. Backend-only changes do not claim browser/product UI acceptance.
