## Actual exports and owner seams

- `createFactoryStore(pool, authorize, botId = null, lifecycle?)`: third argument remains Bot identity. Fourth argument is `{gates?, independent?}`. No lifecycle argument preserves intake-only behavior. `gates` maps review/verify/approval/publish/monitor to `(tx, task, attempt, finishChange) => Promise<boolean>`; it executes within the locked transaction. `independent(tx,task,runId)` must pass for both passed and failed review/verify/monitor outcomes. The candidate consumes #193 commit 951cd3d70333ae08ac6d5a0252d946e1f5ff087d and installs its actual v2 predicate for review/verify/monitor. This proves independence only; missing stage receipt/configuration gates still reject.
- `store.lockTask(tx,userId,taskId)` returns the authorized current row after task lock, issue row lock and live issue/source/Bot access checks. `route/read/listForIssue/apply` retain PR385 signatures. `apply(...,existingTx?)` joins without committing caller transactions. Trusted backend lifecycle changes only; worker/model tools expose no finish/candidate/advance action.
- `createFactoryDispatch(pool,store,queue,adapters)` returns `(userId,{binding,agentId,deviceRepoId,note?},existingTx?) => Promise<FactoryDispatchResult>`. Result extends snapshot with `runId,replayed,binding`. `queue(tx,userId,{issueId,agentId,deviceRepoId,note?},botId)` reuses current main queueRun through the existing database scope. `adapters.configure[stage](tx,task,runId)` and `adapters.freeze(tx,task,runId)` must complete before bind. Missing configurators deny dispatch. One task/attempt ledger checks the entire input; queue/configuration/freeze/bind/receipt commit atomically. Replay after progression is stale; stop/revocation/access checks precede replay.
- `factoryRuntimeForBot(botId,lifecycle?,configure?,validateCheck?,consumers?)` wires actual queueRun, frozen worker configuration, questions and reconciliation. Consumers own their real review/verify/monitor configurators and validators. Defaults only support spec/execute configuration; other stages fail closed. `consumers` maps review/verify/monitor to `(tx,store,task,run)=>Promise<unknown>`; ownership-specific receipt logic is not duplicated here.
- `createFactoryClaim(store,questions,validateCheck?)` returns `(tx,userId,deviceId,runId,leaseExpiresAt)=>Promise<assignmentExtras>`. Existing local/cloud claim invokes the Factory guard before the run lock/update and token issuance. Unbound retry ancestry, stale attempt/candidate, stopped tasks, access loss and wrong owner/device reject. Consumers provide their current frozen-assignment checker. A true independence predicate alone grants neither pass nor execution permission.

Task binding remains `{taskId,issueId,attemptId,revision,candidateId}`. Attempt run/session and candidate provenance is append-only across retries. A candidate cannot be replaced within the same execute attempt. Monitor retry accepts only the same candidate's passed monitor attempt (or existing failed/blocked recovery), creates a new pending attempt with increased ordinal/position/revision and empty run/session/evidence, and leaves the old attempt unchanged. Publication validation remains #194/#195's responsibility inside the supplied monitor configurator/gate; absence blocks normal monitor dispatch.

## Questions and recovery

`createFactoryQuestions(pool,authorize,store,dispatch,validateCheck?)` exports `record`, `read`, `list`, `pending`, `escalate`, `answer`, `claimContinuation`, `settle`. Question identities bind task/issue/candidate/stage, origin attempt/run/session and revision. New questions persist a server-owned 24-hour response deadline; reads/answers/claim evaluate it without adding a timer. A recorded question moves running to waiting (origin+1), never cancelled. Answer retry creates a fresh same-stage attempt then dispatches it (waiting+2). Exact answer IDs/fingerprints replay without a second run; changed answers conflict. Model context answers accept only exact issue/original-request facts; decisions/permissions/external blockers require the authenticated human path and do not grant new execution/publication permissions.

The separate `/api/factory/questions/[questionId]` route requires a live browser session, rejects Authorization credentials, enforces same-origin POST and resolves actual owner/Bot scope. `POST /api/coordinator/messages` remains strict text/submissionId; no hidden question metadata is restored. Question references are `{questionId,questionRevision,binding,originRunId,originSessionId}`. Human answer is `{reference,answerId,text}`; no model-supplied actor mode.

Existing ask_human/report_blocked hand-in records the question; the existing Coordinator wake and preparePrompt reconciliation consume persisted run state. Reconciliation settles a previous continuation before interpreting its completion, and applies subsequent changes using refreshed bindings. No new wake queue or scheduler is added. Claim returns `{continuesRunId,resumeSessionId,followUp,requireSessionResume:true,questionId}`. The daemon rejects missing resume capability/worktree or a mismatched resumed session; it cannot silently fall back to a new session. Actual provider resume is still unverified.

## Migration and default-off approval inventory

This undeployed candidate renames PR385’s `20261028070000_factory_192_routing.sql` without changing its SQL bytes because main now contains later migrations. Apply exactly one name, never both; PR385 itself remains unchanged.

Candidate intake migration: `20261028182316_factory_192_routing.sql` creates four Factory tables/indexes with issue foreign keys. No ordinary application columns or data are rewritten. It still takes DDL/catalog and referenced-table locks during installation; default-off is not permission to execute production SQL.

Candidate migration: `20261028182317_factory_192_questions.sql` creates Factory questions/indexes and adds nullable JSONB `agent_runs.questionContinuation`. ALTER TABLE requires an ACCESS EXCLUSIVE lock even though there is no backfill/default. The new column is accessed only in explicit Factory raw SQL; it is deliberately absent from ordinary Drizzle all-column projections, so default-off ordinary reads/writes do not require it. Historical event references do not block Bot deletion. Existing issue cascades also delete the new Factory state when an issue is deleted; no deletion operation is performed by these migrations.

Both `MIKKA_FACTORY_ROUTING_ENABLED=1` and `MIKKA_FACTORY_LIFECYCLE_ENABLED=1` are necessary for runtime entry. Off returns before Factory SQL in claim, question HTTP and Coordinator preparation. Tool registration does not expand existing frozen grants. No environment flags, credentials, external DB, provider permission or paid operation has been changed. Production approval must name target database, exact two-file manifest/checksums, lock window, backup/recovery expectations and the intended flag/grant rollout separately. Only disposable isolated PostgreSQL was used here.
