# Factory flow v2 backend contract (#1276)

Implements the backend portion of [the 2026-11-04 decision](../design/decisions/2026-11-04-2200-factory-flow-like-warp.md).
The stored lifecycle remains compatible with existing workers and v1 tasks.
The public projection names the stages `triage`, `spec`, `implement`, `review`,
`handoff`, `completed`, and `cancelled`. It lists only visited stages. A merged
receipt for the current candidate is required for `completed`; a closed PR,
finished run, passed review or handoff is insufficient.

## Observations and the single review

The existing `passed` boolean is retained for older workers. New workers may
also submit `status: passed | failed | unverified`, `reason`, and `resolution`
for a criterion. `unverified` requires `passed: false` and a nonempty reason.
A missing tool, environment or inferable check command is an unverified
observation; it must not be represented as a successful check or a request for
the person to supply a command. Native MCP submission, handoff files, daemon
report normalization and task detail preserve these fields.

A review submits `reviewVerdict: passed | changes_requested | needs_judgment`.
The host retains the fixed candidate SHA, independent session, read-only work
and persisted evidence gates. A real failed daemon check remains a failure.
An ambiguous finding or an unavailable observation reaches human handoff.
A clear finding goes back to implementation, then to handoff on the same task
without a second review. The existing task-wide review limit and flow-v2
skip of the standalone verify stage remain authoritative.

Implementation owns validation. Its frozen prompt asks it to infer useful
repository checks, report actual results, record UI captures (video by
default), retain reviewed criterion identifiers when repairing, and describe
how each finding was resolved. A reviewer receives the acceptance Artifact's
candidate-bound ID, version, hash and byte size alongside producer
observations. A report's existence is not independent proof of correctness.

## Browser flow API

`GET /api/factory/tasks/:taskId/flow` returns a private, uncached projection:

```json
{
  "version": 2,
  "id": "task UUID",
  "issueId": "issue UUID",
  "botId": "mentioned Bot UUID",
  "revision": 12,
  "stage": "handoff",
  "stages": ["implement", "review", "handoff"],
  "needsYou": { "kind": "pr_review", "since": "2026-11-05T00:00:00.000Z" },
  "review": {
    "verdict": "needs_judgment",
    "candidateId": "reviewed candidate UUID",
    "currentCandidateReviewed": true
  },
  "acceptance": {
    "artifactId": "Artifact UUID",
    "version": 2,
    "runId": "implementing run UUID",
    "candidateId": "current candidate UUID",
    "counts": { "passed": 2, "failed": 0, "unverified": 1 },
    "media": []
  },
  "pullRequest": { "url": "https://github.com/owner/repo/pull/1", "state": "open" }
}
```

`needsYou` is absent when no human action is required. Its kinds are
`spec_review`, `question`, `pr_review`, `blocked`, and `failed`. Questions come
from durable `factory_questions.status = waiting_user`; raw run
`waiting_input` does not create human waiting time. A repaired candidate keeps
the original review's candidate ID and has `currentCandidateReviewed: false`.
The acceptance projection includes only a report bound to the current candidate.
During repair or a new request, it is absent until the new candidate report is
ready; previous Artifact versions remain available as history.

Both methods require a live browser session. An Authorization header, PAT or
delegated credential is rejected. GET uses the canonical task/Bot/source/issue
access check and a repeatable-read snapshot. It does not mutate application
data. Existing Factory APIs remain available for old consumers.

`POST` on the same path accepts only:

```json
{
  "operation": "approve_spec",
  "input": {
    "binding": { "taskId": "task UUID", "revision": 4 },
    "eventId": "unique click UUID"
  }
}
```

The POST requires the application Origin. Approval locks the current task,
checks its revision, a completed v2 spec and the successful submitted native
run, then records the human session digest and advances/dispatches in one
host-owned Factory transaction. Repeating the same click returns its receipt;
a stale revision cannot approve new work. A model-side `advance` without the
receipt returns the localized `factory_spec_approval_required` error. Known
Agent Profile refusals retain their original HTTP status, error code and detail;
unexpected failures preserve their original exception and cause.

The first implementation after approval resolves an executor profile for the
`execute` stage. It does not inherit the planner's read-only flag, frozen role,
thread-run grant or native-session continuation. Ordinary repairs retain their
existing frozen executor behavior and host authorization checks.

## Acceptance Artifact and task comments

One Markdown Artifact is associated with the Factory task and issue. Its
versions are generated from the implementing agent's structured observations,
plus the task's original review and real capture metadata. The host does not
invent an observed pass, resolution, line count, PR or screenshot. Unverified
criteria and reasons appear first, with command/output and evidence adjacent
to each criterion. Missing review resolutions are explicitly left for human
judgment. Current-candidate review findings that are failed or unverified enter
the current counts and first section, including findings absent from the original
implementation report. The report keeps implementation and review observations
distinct and retains both reasons. A review of an earlier candidate is labeled
as history and does not change the current counts; even an empty evidence field
cannot hide its reason.

Each version retains its own execution identity and submission receipt; the
Artifact's original creating run is immutable. The report updates after
implementation, review and repair completion. Hash-identical retries create
no new version. The existing ArtifactWindow opens it via `?artifact=<id>`.
Capture URLs use the existing authenticated capture API. `acceptance.media`
contains at most 40 entries with capture ID, kind, URL, title, run ID and
criterion association for the frontend media renderer.

The mentioned Bot writes one persisted comment per visited public stage in
the task's own comment thread. State changes within that stage update the
same deterministic comment ID. There is no new Coordinator dispatch message,
worker, timer or polling loop. Existing document and Artifact live events are
emitted after transaction commit. Concurrent tasks on one issue serialize
document edits on the document row. A missing document is inserted with conflict
handling before locking and re-reading it, so neither task overwrites the other
and no canonical issue SHARE lock is upgraded.

## Read budgets and migration

The public projection performs two bounded reads after canonical task access:
one current-attempt row with projected review verdict, PR fields and Artifact
metadata, then at most eight grouped stage rows. It does not fetch run prompts,
transcripts, complete reports or lifecycle snapshots. A real PostgreSQL fixture
measures both JSON response sizes and projected database result rows; these
are serialized row/payload bytes, not a claim about Neon transport framing.
The handoff fixture returned 6,244 bytes (6.10 KiB) through the full lifecycle
snapshot versus 927 bytes (0.91 KiB) through the public flow. The two new
projected result sets were 696 and 100 bytes (0.78 KiB combined); the Markdown
report was 812 bytes (0.79 KiB). Canonical authorization/task reads precede
both paths and are not included in the new-projection figure.

Report generation is transition-driven. It reads one producing run projection,
one review projection and at most 40 ready capture metadata rows. Each report
projection caps criteria at 200, files at 100 and every text field. Rendered
Markdown is bounded below the existing 1 MB Artifact limit, including 200
maximum-length multibyte implementation criteria and a bounded union of 200
implementation plus 200 current-review observations. The existing issue Yjs document is read
only when the stage comment's content hash changes; this is an existing
bounded document, not historical run/transcript loading.

The additive, idempotent migration creates task-to-Artifact, per-stage comment
and browser spec-approval receipt tables. Its local test-only filename
`20261105114700_factory_flow_view.sql` is temporary: Coordinator must assign the
final number after the latest main migration, and the ordering gate must pass
before publishing. Normal build migration applies it; there is no background
backfill or production data repair in this change.

## Frontend and acceptance integration still required

The frontend must use this stage/needsYou projection, show the human spec
approval action, open the existing ArtifactWindow and render its media with
the existing authenticated image/video components. It must stop inserting
internal dispatch runs into Coordinator chat for this flow. Follow the
existing live invalidations; do not add a refresh interval.

This backend change does not create a draft PR for the specification. Current
plan workers submit their specification through the existing plan contract;
the decision's draft-PR presentation and approval wiring need coordinated
integration before claiming that full interaction accepted. The Markdown
renderer displays images and video links; inline video playback also needs
the frontend media integration. No Artifact iframe/CSP restriction is relaxed.
A late PR-publication update is available in the flow projection immediately;
the Markdown report reflects the PR data present at its last completion-driven
version update.

Local synthetic captures and provider fixtures verify persistence, boundaries
and rendering contracts. They are not real visual or provider acceptance.
End-to-end acceptance must still use the two authorized subscription paths
(`claude-haiku-5-5` and `gpt-6-luna`) and the deployed commit. DeepSeek/API-key
acceptance is not a merge gate. Production acceptance and closing #1276 wait
for the integrated human-facing flow and recorded deployment evidence.
