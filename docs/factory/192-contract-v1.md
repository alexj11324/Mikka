# Factory state contract v1 (issue #192)

Frozen against main 7c11935f1965915986a44ae2a311b1a0378171af. Consumers: #191 dispatch, #193 review/verification, #194 approval, #195 recovery monitoring. `lib/factory/contract.ts` is the machine readable source. Changes to this version require coordinated consumers.

Identity is `(userId, issueId, taskId, attemptId, revision, candidateId)`. The server derives userId from authenticated identity, never tool arguments. Every mutation carries an eventId plus the full binding; revision is a compare-and-swap fence. A duplicate event returns its recorded result only for an identical payload and binding, after current authorization/terminal checks. Stale attempts, changed candidates, foreign owners/issues and changed replay payloads fail closed.

Stages: `clarify → spec → execute → review → verify → approval → publish → monitor`. Clear, authorized tasks start at execute. Only actual missing information or missing permission starts clarify; needsSpec starts spec only when no missing items remain. Clarification records missing items and their source Coordinator event. It must not invent permissions. Clarify may resolve directly to execute. No mandatory spec or fixed agent count.

Status: pending, running, waiting, passed, failed, blocked, cancelled, revoked. Task holds current stage/attempt/revision/candidate and latest reason; immutable attempts retain run/session, output, evidence, failure and recovery reasons. One stage's completion cannot implicitly pass another gate. No automatic publish, merge or external action is supplied by this issue.

Candidate identity is a UUID plus exact 40-character SHA, repository, environment and scope. Candidate rows are immutable. Replacement is only in execute and clears downstream eligibility by replacing candidateId and bumping revision. #193 must use distinct run/session identities for execute, review and verify; #194 must bind approval to this exact candidate identity plus action/target/expiry, and recheck the full fence transactionally before consuming it. #195 links original task/issue/candidate and creates a fresh repair attempt; cancellation and revocation block repairs.

`createFactoryStore(pool, authorize, gates?)` uses the existing request-scoped PG pool. `route(userId, input)` returns persisted task/attempt; `read(userId, taskId)` reads histories; `apply(userId, binding, eventId, change, existingTransaction?)` applies one transaction. `authorize` must re-evaluate existing issue/team/deletion access, not a cached grant. The task owner is always checked as well. Cancelling/revoking stops bound live agent_runs in the same transaction. A retry creates a fresh stage attempt; restart recovery reads/replays the original attempt and never queues a run. `resolve` consumes a subsequent authenticated user_message to record clarification resolution (actual dispatch grants remain #191 checks). `repair` from failed/blocked/waiting review/verify/monitor creates a fresh execute attempt and clears candidateId. `bind_run` accepts only an existing same-owner/same-issue run and captures its actual session. The optional existingTransaction is the caller-owned PoolClient; the caller must begin and commit/roll back the full operation, including on any thrown error. Dispatch creation remains #191's responsibility and must join its transaction with the stage binding before runtime integration is accepted; do not use queue-then-bind across a crash boundary.

Evidence references include artifact, kind, runId, sessionId, candidateId, SHA, environment and timestamp. Pre-candidate spec evidence uses null candidateId/SHA; clarification resolution references the actual subsequent Coordinator user_message. A pass requires persisted real completed run/session provenance plus matching candidate evidence. Model tools cannot call finish/pass, advance, candidate, retry or bind_run. #193/#194 supply their own trusted evidence/approval validators; review/verify/approval/publish/monitor cannot be passed without their explicit consumer validator in `gates`; the default adapter installs none. Model claims and daemon self-report alone do not establish independent review or real verification.

Migration reserved: `drizzle/20261025010001_factory_192_stages.sql` (independent UTC timestamp). No dispatch, wake, Harness, BYOS or frontend changes. Automatic advancement remains dependent on #176 reliable wake. Real PG/API isolation is layered evidence; final completion additionally needs #191 integration, fixed cloud Preview, actual chat/Harness and #181 same-version acceptance.


## Fixed #191 integration

Integrated parent-supplied dispatch commit `123f7a2eed015623fbbb489a5473c7e757d143d2` on this candidate only. Existing `insertRunOnce` semantics and request-key fingerprint are unchanged. `queueRun` accepts an optional transaction executor; default callers retain their existing behavior. `createFactoryDispatch` locks the task, joins #191's request-key/issue transaction via `factoryDispatchDatabase`, and binds the run plus event ledger before one COMMIT. The requestKey is `factory:<taskId>:<attemptId>`; dispatch eventId is the attemptId. Changing agent/repository/note on a replay still hits #191's fingerprint rejection.

Coordinator tools now persist route/clarification and require the exact binding for dispatch. Only backend reconciliation can pass spec/execute, by reading existing terminal agent_runs/session/report and exact published SHA; execute additionally requires the daemon's persisted submitted/verify-passed result. Review and later gates remain closed by default. Reconciliation runs during existing Coordinator prompt preparation and does not add a wake mechanism. Cancelled/revoked tasks are excluded; failed or incomplete terminal records remain failed/blocked. Artifact references are checked against actual stored run report/chunks.

Cloud Preview deployment was denied in the parent-coordinated batch pending user authorization. No deployment retry is made here. All current CI run/session/report fixtures are explicit layer tests, not a claim of real Harness or Preview acceptance.

After main advanced to `99ec7e1` with migrations through `20261025005600`, the imported, undeployed #191 migration was renamed on this candidate only to `20261025011101_run_dispatch_keys.sql` to satisfy the existing migration-order policy. The original #191 branch is unchanged. The #192 migration remains `20261025010001_factory_192_stages.sql`. Attempt history has a per-task monotonic `position` in addition to its per-stage `ordinal`.

Historical candidate/attempt run IDs deliberately survive the existing Agent-to-run deletion cascade. They are validated against current agent_runs ownership/issue/session before mutations or evidence passing. If an Agent deletion removes a bound live run, reconciliation persists blocked with the historical run ID; this preserves deletion behavior and prevents success from missing evidence.
