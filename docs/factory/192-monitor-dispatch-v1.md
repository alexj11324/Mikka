# Normal monitor dispatch (#192 compatibility increment)

Base: #195 integration `e5d88921d4c6981535e2d8056cef503726d9f586`. This increment repairs the normal Factory dispatch allowlist and configuration/claim path; it does not modify #195 monitor, probe, publication receipt readers or its branch. No migration or frontend change.

Only a current pending monitor attempt with a non-null, matching candidate can start a new run. The existing task/access lock is held while the existing #195 `readFactoryPublicationReceipt` validates the current candidate's successful publication, actual verified target receipt, matching publish output and unrevoked human approval. Only deploy_preview observations with a non-merge target are supported here; monitoring does not authorize another publication.

Normal dispatch keeps #191's stable attempt request key, parameter fingerprint and issue overlap gate. Under that same transaction it freezes the receipt identity, candidate, target/environment/reference, repository command and repository ID in the existing attempt output; it creates an acceptance run pinned to the exact SHA and binds it before commit. No queue-then-bind boundary, timer, new run queue or state source is introduced. The existing validator callback is unchanged.

The existing check claim path recognizes monitor attempts and delegates to the new #192 monitor assignment helper. It rechecks current task/attempt/candidate, access, publication/approval revocation, exact frozen receipt, device/agent/repository identity, installed Harness, online/enabled device and queued live run. The assignment uses the same existing read-only acceptance policy: no dependency installation, writes outside the repository or git push. The command remains frozen even if the repository's configured command later changes. #195's trusted target probe still runs through its existing completion/consume path; a valid historical receipt does not claim the target is currently healthy.

Exact dispatch replay returns the same bound run only while its same monitor attempt remains current and live. A different parameter fingerprint, candidate or attempt, completed/failed/waiting/blocked monitor, cancellation, revocation or missing receipt fails closed. Approval expiry after a consumed publication does not erase that publication; revocation blocks both dispatch replay and subsequent claim. No permission or provider authorization is created by this path.

Layer tests create a real local publication through #194's adapter/approval/evidence reader using explicit synthetic identity and upstream Harness conclusions. They then exercise normal #191 queue/Factory dispatch, ten-way replay, actual read-only claim validation, #195's real local child-process probe/consume and a subsequent monitor cycle. Wrong owner/candidate/repository/agent, replaced candidates, receipt tampering, revocation, terminal states and precommit SQL interruption/reconnect are checked against disposable PG17. These are local/CI layer evidence, not a cloud deployment, real OAuth/Harness or #181 same-version acceptance claim.

The execution-question repair has a separate contract and commits; it is not part of this dispatch increment.
